# Kegare: Design

A cursed-energy combat framework for **NeoForge 21.1.x / Minecraft 1.21.1 / Java 21**, built mainly for **PvP with friends**.
It covers the base systems (§3.1–3.13) and the content built on them: specials (§3.15), the loadout (§3.16), Reverse
Malice Technique (§3.17–3.18), the innate techniques Rime (§3.14), Swap (§3.19), Puppet Manipulation (§3.20) and Time Manipulation (§3.26), and
progression (§3.21). Mobs (the Kegare), dominions and lore come later (§5).

- Mod ID: `kegare` · Package: `com.cnethuka.kegare` · Build: ModDevGradle MDK
- Everything is server-authoritative. Clients send key intents and render what the server syncs.

---

## 1. Naming rule

**Code IDs match the display names.** That covers class, package and variable names, attachment and registry IDs,
config keys, lang keys and command names.

| Concept | Code ID | Display name |
|---|---|---|
| Cursed energy | `malice` (`MaliceData`, `kegare:malice`, `/kegare malice`) | Malice |
| Per-player power | `innate_technique` (`InnateTechnique`, `kegare:innate_technique`, `/kegare innate`) | Innate Technique |
| Ultimate space (future) | `dominion` | Dominion |
| Zero-Malice flag | `severed` | Severed |
| Reroll item | `purification_talisman` | Purification Talisman |

- **Every player-facing string lives only in `en_us.json`**, which is generated by
  `data/KegareLanguageProvider.java`. No hardcoded text: messages, HUD, commands and advancements all use lang keys.
  The display terms are constants at the top of that provider.
- **"Kegare" is the mod name.** It is reserved as the name of the future hostile spirit mobs, and is never used for
  the energy.
- **Safety nets:**
  - Datagen fails if any registered innate technique, ability or trait has no lang entry, or if a non-test innate
    technique has no epithet (§3.3).
  - `LangKeysTest` fails if code uses a message/command/HUD/key lang key that isn't in `en_us.json`.
- **Known exception:** config comments (`kegare-server.toml`, and the config screen tooltips that fall back to them)
  are written in code.

### Design rule: secret identities

**Any advancement that would reveal a secret identity is hidden and never announced to chat.** That means anything
showing who holds a unique trait (e.g. six_eyes). Only the earner sees the toast, so the
game never names a bearer, heir or killer of a secret holder.

- **Enforced in code:** `KegareAdvancements.SECRET_IDENTITY` lists every such ID. The advancement generator forces
  them hidden and silent, and datagen fails if one ever isn't.
- **Current:** `clear_sight`, `the_cycle_continues`, `eyes_closed`, `blinded`.
- **Reserved for later content:** a few more IDs are already in the set, so they're covered automatically once they're
  generated.
- **Adding a new secret advancement:** add its ID to the set first.
- **Exception: a secret tab root may be visible (never announced).** A tab only appears to players who have earned
  something in it, so a visible root reveals nothing to uninvolved players. A hidden root is never drawn until
  earned, so everyone else would see a connector line pointing at nothing.
  - The exception applies only to roots listed in `KegareAdvancements.SECRET_VISIBLE_ROOTS`.
  - Datagen fails if a listed ID has a parent, or if any other secret advancement is visible.
  - Current: `clear_sight` (Six Eyes tab).
- **Messages never name a unique trait.** No death message, chat line or action-bar message may say "Six
  Eyes" or any other unique trait's name, or say who holds one. Op debug commands are the exception (`/kegare trait`,
  `/kegare info`): operators see everything anyway. A player born with a unique trait learns it from the private roll
  reveal (§3.12), not from chat.
  - **Techniques aren't secret identities,** so kill messages may name them ("blown apart by %s's puppet", "tangled up in
    %s's strings", "frozen solid by %s").
- **Related rule: PvP information is silent.** Advancements that would leak combat-relevant information get no chat
  announcement, even though they aren't secret identities. They live in `KegareAdvancements.SILENT`, and datagen
  enforces it.
  - Current: `overflowing` (reveals Malice capacity), `chosen_by_fate` (reveals a Legendary roll), and
    `a_green_light` / `its_been_a_while` (reveal that a player can heal), and `moving_up`, `proven`, `recognized`,
    `outside_the_ladder`, `full_kit` (Grade and Refinement are private, §3.21). The heal ones and the progression ones are
    also **hidden** until earned (`KegareAdvancements.SILENT_HIDDEN`, enforced by datagen).
  - Innate technique tab roots are silent for the same reason (§3.11).

## 3. Systems

### 3.1 Malice (fixed at birth)
- **First join** rolls a tier once. Weights, bases and regen come from config (`[malice.tiers.<tier>]`):

  | Tier | Weight | Base capacity | Rolls between | Regen per second (`regenPercentPerSecond`) |
  |---|---|---|---|---|
  | Zero | 2 | 0 | 0 | none |
  | Low | 30 | ~250 | 225–275 | 3% of capacity (7.5/s at base) |
  | Average | 45 | ~600 | 540–660 | 2% (12/s) |
  | High | 20 | ~1500 | 1350–1650 | 1.5% (22.5/s) |
  | Vast | 3 | ~10000 | 9000–11000 | 0.75% (75/s) |

  Non-zero tiers get a uniform offset of up to ±`capacityVariationPercent` (10%) of their own base, and never land on 0.
- **The scale:** every ability's cost, upkeep and special cost, Possess's backlash included, is set so that Low
  buys about six Frost Shards, or two and a half seconds of RMT. Higher tiers buy far more, on purpose. All of it is in
  config.
- **Capacity never changes.** Death, rerolls and items leave it alone. The only exceptions are admin debug
  (`/kegare malice capacity`, `/kegare rebirth`). A capacity set by hand takes the regen of the tier with the nearest base.
- **Reserve** (`current`) is spent by abilities and regenerates at its tier's percentage of capacity per second.
  Regen pauses for `regenPauseSeconds` (5s) after dealing or taking damage.
- **New defaults don't reach an existing config.** NeoForge keeps whatever an existing `kegare-server.toml` holds and only adds
  missing keys, so a changed default only reaches it through a migration (§3.9). Delete the file
  to get the defaults, then `/kegare rebirth` to re-roll a player's capacity.
- **Tests:** `MaliceRollerTest` (the tier roll against the weights, every offset of each tier's range, never 0),
  `MaliceRulesTest` (regen arithmetic), `MaliceScaleTest` (the shipped defaults, Low's budget, regen by tier on a player, the combat
  pause).
- **Respawn** refills the reserve to capacity.
- **Severed** = born with 0 capacity. The player gets no innate technique, can't reroll, and the HUD is hidden.
  Only the flag is stored; their superhuman body comes from it (§3.27).
- **Becoming Severed** (birth or rebirth roll of 0, `/kegare malice capacity <player> 0`, or any future path):
  - Every `requiresMalice` trait is stripped (*"The eyes have closed."*).
  - Unique inheritable ones (six_eyes) go through the **normal transfer** (30s, then an eligible heir).
  - Other Malice-based traits are removed; a unique non-inheritable one is released.
  - This is enforced in one place: `MaliceService.applyCapacity` is the only code that can change capacity or the
    Severed flag, because `MaliceData`'s setters are package-private. Any new path therefore triggers the strip.
  - Login re-checks it as a safety net.
  - Rebirth re-rolls Malice *before* wiping traits, so rebirthing into Severed also transfers the eyes.

### 3.2 Traits
- A registry (`kegare:trait`) plus a per-player ID set (saved, synced, kept on death unless noted below).
- `Trait.Properties` flags:
  - `unique`: at most one bearer per world.
  - `requiresMalice`: never rolled for, inherited by or granted to a Severed player.
  - `inheritable`: passes on when lost.
  - `lostOnPvpDeath`: removed when the bearer is killed by another player.
  - `birthChance`: read from config.
- Hooks: `onAdded(reason)` (BIRTH / ADMIN / INHERITED), `onRemoved(reason)` (ADMIN / REBIRTH / LOST_IN_PVP /
  RELEASED / REVOKED / CONFLICT / SEVERED), `onBearerKilledByPlayer`, `canRollFor`.
- **World record** (`UniqueTraitSavedData`) holds:
  - bearers
  - pending successions
  - offline revocations
  - last-seen times
- **Login reconcile:** applies revocations, drops unknown IDs, re-claims a lost claim (world record wiped), and
  strips unique traits held by someone else or in succession.
- **Release** (`/kegare trait release <trait>`, or `uniqueTraitInactiveDays`) frees a unique trait from its holder:
  - an online holder loses it immediately
  - an offline holder loses it on their next login (revocation)
  - an inheritable trait then passes on (below)
- **Succession** (`TraitSuccession`): an inheritable trait that loses its bearer becomes *pending*.
  - Birth rolls can't take a pending trait.
  - After the trait's delay, it goes to an heir chosen by `TransferRules`: online, not Severed (if it needs
    Malice), not the previous bearer.
  - RANDOM picks any eligible player. KILLER picks the killer if eligible, otherwise random.
  - If nobody is eligible, the next eligible player to log in gets it.
  - Admin `trait give` overrides a pending succession.
- **`kegare:six_eyes`** (unique, requiresMalice, inheritable, lostOnPvpDeath, 1% birth, **no gameplay effects**):
  - **Killed by another player** (direct hit, or kill credit, e.g. knocked into the void): it is stripped before
    respawn, and after `sixEyesTransferDelaySeconds` (30) it opens in an heir per `sixEyesTransferMode`.
    Everyone sees the anonymous broadcast *"The eyes have closed... and opened elsewhere."*
  - **Any other death:** the bearer keeps it.
  - Advancements live in their own **Six Eyes tab** (§3.11). They are hidden and never announced in chat
    (secret-identity rule, §1); the earner still gets the toast. *Eyes Closed* covers every loss: PvP, release,
    revocation, or becoming Severed.

### 3.3 Innate technique framework
- Registry `kegare:innate_technique`, synced to clients so the HUD can resolve names and ability lists by ID.
- `InnateTechnique` is made of:
  - a rarity (COMMON / RARE / EPIC / LEGENDARY)
  - an ordered **ability list**, cast with the number keys in Technique Mode (§3.5); each ability may
    have a **special**, with R (§3.15)
  - an optional **ultimate** (the ultimate key, where dominions will plug in)
  - a **Malice color** (`Builder.maliceColor(0xRRGGBB)`, read with `maliceColor()`; default Malice purple
    `#9D4EDD`, `InnateTechnique.DEFAULT_MALICE_COLOR`). It colors the Malice bar's fill, glow and ghost fill on the
    HUD and the Sorcerer screen, and the Technique Mode glow. Display only: definitions are registry-synced, so the
    client looks it up from the synced innate technique ID, and it changes the moment the technique does (reroll,
    admin, rebirth). Rime uses deep blue `#1E3A8A`; the test techniques keep the default.
  - an **epithet** (lang key `innate_technique.<namespace>.<id>.epithet`, read with `epithet()`): one short line that
    says what the technique feels like, shown under its name on the Sorcerer screen and typed out in the Epic and
    Legendary reveals (§3.12). **Every non-test innate technique sets one; datagen fails without it.** Test techniques
    use "[Test]". Rime: "Breath Turned to Glass". Swap: "Nothing Stays Where It Was". Puppet Manipulation: "Strings
    Without a Stage".
  - an optional **signature animation** (`Builder.signatureAnimation(id)`, a PAL animation, read with
    `signatureAnimation()`): what the player model does beside the emblem on the reveal's name card. Without one the model
    just stands there. Rime: `frost_shard_cast`. Swap: `positions_clap`. Puppet Manipulation: `puppet_create_release`.
  - the hooks `onAssigned` / `onRemoved`
- `Ability` interface: `cost`, `cooldownTicks`, `castType`, `upkeepPerSecond`, min/max charge, max channel,
  `canCast`, `execute`, `tick`, `onEnd`, plus `special`, `cooldownKey` and `requirements` (§3.15). Costs take the
  caster so traits can scale them later.

  | Cast type | Lifecycle (server, `CastManager`) |
  |---|---|
  | INSTANT | press → validate → pay cost → `execute` → cooldown |
  | CHARGED | press → validate (cost checked) → charge (`tick`) → release ≥ min charge → pay → `execute(charge 0..1)` → cooldown. Early release or stun cancels free |
  | CHANNELED | press → validate → pay start cost → `execute` → each tick pay upkeep/20 + `tick` → release / out of Malice / max duration / stun → `onEnd` → cooldown |
  | TOGGLE | press → validate → pay activation → `execute` → each tick pay upkeep/20 + `tick` → press again / out of Malice → `onEnd` → cooldown. Stuns don't end toggles |

- Shared checks in `CastManager.tryCast` / `validate`:
  - **unlocked by Refinement, checked first** (`TechniqueUnlocks.isUnlocked`, §3.21): a locked ability, special or ultimate
    fizzles with "Requires Refinement X.", no cost and no cooldown
  - alive and not Severed
  - has an innate technique
  - not busy (one charge/channel at a time)
  - **not stunned**
  - off cooldown (by `cooldownKey`, so a special and its base share one)
  - every `Requirement` met (unmet: fizzle with a message, nothing paid)
  - can afford the cost
  - `ability.canCast`
- An INSTANT ability can still fizzle AFTER paying: `CastManager.fizzleKeepingCost` from its `execute` keeps the
  Malice spent but starts no cooldown and plays no cast visuals (Swap uses it when `SwapTargetEvent` is cancelled,
  §3.19).
- Charges, channels and toggles are runtime-only and end on death, logout and innate technique change.
- **Every cast runs inside a `CastScope`** (execute, tick and end), which is what traces a hit, an effect or a spawned
  entity back to its ability. It's how every technique gets Refinement and Assessment with no code of its own (§3.21).
- **Unlock levels:** every non-test technique calls `Builder.defaultUnlockLevels()` and/or `Builder.unlockLevel(ability, level)`;
  datagen fails without one (§3.21).
- **TEST CONTENT** (`innatetechnique/test/`, config `[test_abilities]`, everything unlocked):

  | Innate technique | Rarity | Abilities |
  |---|---|---|
  | `test_kinetic` | Common | Dash (instant), Burst (charged) |
  | `test_flux` | Rare | Hover (channeled), Aura (toggle) |
  | `test_prism` | Epic | Burst (charged), Hover (channeled), plus Shockwave (instant ultimate) |
  | `test_apex` | Legendary | all four, plus Shockwave (instant ultimate) |

  There is one per rarity, so every reveal can be shown. Two test specials exercise §3.15: **Blink** (special of
  Dash, instant short teleport, requires Aura to be active) and **Updraft** (special of Hover, charged upward launch,
  requires the `six_eyes` trait). Burst, Aura and Shockwave have none, so R fizzles on them.
  Set `includeTestInnateTechniques=false` once real innate techniques exist.

### 3.4 Rolls and pity
- Weighted rarity roll (Common 50 / Rare 30 / Epic 15 / Legendary 5), then a uniform pick within that rarity.
- **Never rolls into the current innate technique.** Rarities with no eligible innate technique get weight 0.
- `rollsSinceLegendary` = completed rolls since the last Legendary, so the roll in progress is number n = counter + 1.
  - **Soft pity:** n > 30 adds (n − 30) × 5 to the Legendary weight (roll 31: 10, roll 49: 100).
  - **Hard pity:** n ≥ 50 is a guaranteed Legendary.
  - **Reset** on any Legendary.
  - If the only Legendary is your current innate technique, pity can't fire and the counter keeps climbing.
- **First join:** roll Malice, then traits, then an innate technique (unless Severed), and award *Awakening*.
  Severed players also get *Severed*.
- **Purification Talisman:** rerolls the **innate technique only** (Malice and traits untouched). It is refused,
  and not consumed, for Severed players and while in combat (*"You can't purify mid-fight."*). It awards
  *Reawakening*.
- **Roll reasons** (`RollReason`, `PityState`):

  | Reason | Counts toward pity | Reawakening |
  |---|---|---|
  | BIRTH | yes | no |
  | TALISMAN | yes | yes |
  | ADMIN (`/kegare innate reroll`, `/kegare debug reroll`) | yes | no |
  | REPLACEMENT | **no** | no |

  REPLACEMENT is the free roll on login when a player's stored innate technique no longer exists (removed by an
  update). It rolls on base weights (no soft or hard pity), leaves the pity counter and roll total untouched, and
  tells the player *"Your Innate Technique was removed by an update and has been re-rolled."*
- Any Legendary awards *Chosen by Fate* (challenge frame); a hard-pity Legendary also awards *Bitter Luck*.
- Advancements and tabs: see §3.11.
- The pity math is plain Java (`PityRoller`, `MaliceRoller`) and unit-tested (`./gradlew test`).

### 3.5 Input and networking
- **Instant Cast is the only control scheme.** There is no cast key and no select-then-cast. In Technique Mode (**G**):
  - **Number key** (1-9, vanilla's hotbar keys, however they're bound): selects that slot and casts its base ability at once.
  - **Hold R + number key**: selects that slot and casts its special. R can stay held to chain specials.
  - **Charged moves**: hold the number key to charge, let go to fire. A charged special: hold R and the number key, let go of the
    number key to fire. Letting go of R first changes nothing.
  - **R alone**: acts when it comes up, on the selected ability's special, only if no number key went down while it was held. Since
    it can't hold anything, on a charged or channeled special that would start, it starts nothing and says "Hold R and 2 to use
    Glacial Spire." A locked one or one on cooldown still goes to the server, which says why. R's non-cast uses work on the press,
    in and out of the mode, because something R has to end doesn't wait for a number key: `ClientInput.addSpecialKeyNeeded`
    (returning from a possession, §3.20).
  - **V**: the ultimate, on its own key.
  - **What each type does**, base or special: INSTANT fires on the press. CHARGED charges while held and fires on release.
    CHANNELED runs while held and stops on release. TOGGLE switches on the press, on then off, and the release does nothing.
  - **Holding a key never repeats a cast**, and it needs a real press to start anything: auto-repeat doesn't count, nor does a key
    still down as a screen closes.
  - **One hold at a time.** Only the key that started a cast sends its release. While it's really holding a charge or channel, other
    number keys say "Already casting." and do nothing, without moving the selection. Once a cast isn't being held (it was instant,
    the server refused it, it was interrupted, it ran out), the next key casts straight away.
  - An empty slot, a locked ability, a cooldown and the like get the server's usual message.
  - **Nothing gets stuck.** A stun or interruption ends the cast on the server, and the release that follows does nothing. A held key
    outlasts G: the charge carries on and fires when the key comes up. A screen opening lets go of every key, so a charge fires
    with what it has (or fizzles under its minimum), a channel stops, and R alone is cancelled.
- **Right-click is always vanilla**, in and out of Technique Mode: it uses the held item (shield, bow, food) and never casts.
- **Technique Mode** (**G** toggles it). Out of it, number keys and scroll are vanilla, and nothing casts. While it is on, the scroll
  wheel stays on the hotbar, the combat panel takes the hotbar's place and the hotbar becomes a column on the left (§3.6).

  It ends when you press G again, die, or become Severed (or lose your innate technique), and on logout. G does
  nothing for Severed players. Nothing else ends it: chat, any other screen, a command and a dimension change leave the
  mode and the panel as they were. Input and the HUD read one state (`TechniqueMode.isActive`), and it lives on the
  client only: the server has no copy to fall out of step, and turning it on is free, so nothing rides on enforcing it.

  With it off, R and V do nothing. Two things aren't casts and keep working: letting go of a key held since before the mode ended
  (the cast that began gets its usual release), and R to return from a possession (§3.20).
- **Dash and Parry are separate keys** and work while number keys or R are held. Parry's own rule still applies: it's refused during
  a real charge or channel (§3.22). A cast that really starts drops a guard; a press that casts nothing (an empty slot, a locked ability, a cooldown, no target, or switching a toggle off) leaves it up.
- `client/InstantCastKeys` holds all of these rules as plain logic with its own tests. A number key sends
  `SelectAbilityPayload` then `IntentPayload`, which arrive in that order.
- A key tap shorter than a tick still counts as a press.
- C→S payloads are **requests only**, and the server validates each one:
  - `IntentPayload`: which key went down or up (`CastIntent`)
  - `SelectAbilityPayload`: pick a loadout slot (Technique Mode's number keys, just before they cast)
  - `SorcererRequestPayload`: open the Sorcerer screen
  - `TalismanConfirmPayload`: confirm a reroll
- S→C GUI payloads carry results that are already decided and saved: `RevealPayload`, `SorcererInfoPayload`,
  `TalismanPromptPayload` (§3.12), `ProgressionToastPayload` (§3.21, to the earner only).
- S→C `SyncPayload` (owner only) carries: Malice, capacity, tier, severed, innate technique, selected slot,
  cooldowns, active toggles, current charge/channel, traits, and a `ProgressionSnapshot` (Grade, XP, Assessment against
  its requirement, Refinement, Peak Refinement, Insight, §3.21).
  - It is sent at most once per tick, and only when something visible changed (Malice syncs when its whole number
    changes). While regenerating that's 7.5 times a second for Low and 12 for Average, and every tick for High and Vast; a
    Puppet Manipulation player's is 408 bytes, so at most about 8 KB/s, and none once the reserve is full.
  - The client counts down cooldowns locally from game time.
- Swap (§3.19) adds two cosmetic S→C payloads: `Disguises.StatePayload` (the disguise map, to everyone) and
  `SwapLink.Payload` (effects drawn along a line).
- The melee layer (§3.22) has its own payloads: `MeleeIntentPayload` (C→S, requests only), `MeleeDashPayload` and `MeleeHudPayload` (S→C, to their owner), `MeleeTellPayload` (S→C, per viewer: what a ready fist looks like to them). `VisualPayload` carries an optional tint.
- `VisualPayload`'s `START_LOOP` carries how long the loop has been running (`elapsedTicks`, 0 for a fresh start). A
  player who starts tracking an entity gets its running loops with their full `growTicks` and the time already gone, so
  they see each one where everyone else does: a growing loop part-grown, Switchback's countdown at the real time left.
- Network version `17` (since the Impact System's and battle damage's payloads, §3.23 and §3.24; `16` was a loop's elapsed
  time). Bump it when payload formats change; mismatched clients are refused.

### 3.6 HUD
**Rule: the combat HUD does not exist until the player asks for it** (art in `gen_art.py` → `textures/gui/combat/`).
- **Without Technique Mode** the screen is vanilla. Only what can't wait shows, small and under the crosshair
  (`kegare:status`): freeze pips while there are stacks ("Frozen!" while frozen; Severed players too), and a thin
  charge/channel line for a cast still held after the mode ended.
- **G brings up the combat panel** (`kegare:combat_panel`, 250×50, slides up in 0.18 s), drawn at the GUI's own
  scale: ability icons are 16 px, the size of the hotbar's items.
  It **takes the hotbar's place**: the vanilla hotbar, XP bar, level and jump meter are hidden (`HudClearance`).
  - The hotbar stands on the **left edge as a column** (`kegare:combat_hotbar`). It is the **vanilla hotbar**:
    vanilla's own hotbar, selection and off-hand sprites turned a quarter turn (slot 1 at the top, the off-hand
    slot above it), items upright with vanilla's pick-up pop. Chat moves right to clear it.
  - Hearts, food, armour and air sit **on top of** the panel (it raises `Gui.leftHeight`/`rightHeight`), and
    action-bar text, the held item's name and chat move up to match (chat sits just above the hearts, as in
    vanilla).

  The panel:
  - **crest**: freeze pips (pulsing while frozen);
  - **meter housing**: 16 cells of Malice (eight either side of the centre plate) in the innate technique's Malice color (§3.3) with slanted energy streaks;
    spent Malice lingers as a paler **ghost** for 0.45 s, then drains at half the meter per second; gains show at
    once. The current amount sits on the **centre plate**, cyan with a snowflake when the surroundings make casting
    cheaper, orange with a flame when dearer. A thin line under the cells fills while charging (gold) and drains
    while channeling (cyan);
    The number on the centre plate stays full size up to five digits (Vast reaches 11000); only a custom config goes wider, and
    that shrinks to 75%.
  - **tray**: the nine loadout slots (§3.16; 20 px, a 1 px rim round the icon, 2 px apart), then the 24 px ultimate
    in its iron-and-gold frame (a padlock while locked: no Dominion yet, or Refinement hasn't reached it, §3.21). Each slot: icon, its number key as bound (big, bottom-right), cooldown sweep with seconds left, a white flash
    when it comes off cooldown, and a small **R** plate (gold letter if the ability has a special and it's unlocked, dull if not). The
    selected slot is lit gold; active toggles get a green outline, the casting ability a gold one. Empty loadout
    slots show only their number. Grade and XP are never on the combat HUD;
  - accents along the tray and crest in the technique's Malice color.
- The selected ability's name shows above hearts/food for 2 s after a number key selects it (`kegare:combat_name`).
- The melee layer's cues sit under the crosshair, in and out of Technique Mode and for Severed players too, only while there's something to show: **Reinforced** (gold, a Strike is ready), **Dash** and **Recovering** with thin countdown bars (§3.22).
- Severed players never get the panel (G does nothing). Everything is hidden when F1 hides the GUI and in spectator
  mode. Client config `hud.enabled` turns all of it off.

### 3.7 Combat state (`CombatHelper`)
- `markCombat`, `isInCombat` (`combatTagSeconds`, 10s), and `isRegenPaused`.
- `stun(entity, ticks)` never shortens an existing stun and interrupts a charge or channel. `isStunned` is
  respected by every cast. Use `stunTicksRemaining` and `clearStun` to inspect or reset it.
- Players are tagged on dealing or taking real damage (`LivingDamageEvent.Post`). The API works on any
  `LivingEntity` for future systems.

### 3.8 Commands

Every command reads `/kegare <system> <action> [player] [value]`.

- **Permission:** level 2 for everything but `/kegare help`, which anyone can use and which lists only what the sender may run. The root stays open for that one command, so each system asks for the level itself. A non-op who types another command gets vanilla's "Incorrect argument for command".
- **Players:** every player argument takes a name or a selector such as `@a`, and a command given several players runs for each, with a line for each. Where the player is the last argument it's usually optional and defaults to the sender. The console has to name one. The whole-wipe commands (`rebirth`, `progression reset`) always need a name.
- **Short names:** innate techniques, traits and shared abilities go by the path of their ID (`rime`, not `kegare:rime`, which is refused as unknown). Should two mods ever use one short name, Kegare's wins. Suggestions show short names only. Hovering one shows what it is, like "Rime (Rare)" or "Six Eyes (Unique)"; traits have no rarity, so a unique one says so and any other shows only its name.
- **Errors:** an unknown innate technique, trait or Grade points at its list command, and a bad player at `/list`.
- **Feedback:** to the sender only (`sendSuccess(..., false)`), in sentences, with display names and no raw IDs. Everything goes through `CommandArgs.say`. A holder the server has no name for reads "a player this server has no name for", not a UUID. Rarity names take the rarity's color (`InnateTechniqueRarity.color()`, as on the emblem rim). Tier names take `GuiDraw.MALICE` as on the Sorcerer screen, `GuiDraw.GOLD` for Vast as in the reveal, and `GuiDraw.RED` for Zero. GuiDraw's colors are compile-time constants, so a dedicated server never loads that client class. With the vanilla gamerule `sendCommandFeedback` off, players see only errors, as with vanilla commands; the console sees everything.
- **Help:** `HelpCommand.ENTRIES` is written by hand, and `KegareCommandTest.helpMatchesTheCommandTree` holds it to the real tree both ways. Clicking a line in `/kegare help` opens that system, and clicking a command in a system's list types it into the chat box.

### 3.9 Config
- **Server TOML** (`config/kegare-server.toml`, where NeoForge 21.1 keeps server configs; synced to clients and
  hot-reloaded when edited) holds **every balance number**.
  - Sections: `malice` (with `tiers`), `traits`, `roll` (with `weights`, and `includeTestInnateTechniques`),
    `combat`, `rime` (§3.14), `swap` (§3.19), `melee` (§3.22), `impact` (§3.23), `battle_damage` (§3.24), `reverse_malice_technique` (§3.17), `progression` (§3.21), `test_abilities`.
  - The `traits` section includes:
    - `sixEyesBirthChance`
    - `sixEyesTransferMode` (RANDOM | KILLER)
    - `sixEyesTransferDelaySeconds` (30)
    - `uniqueTraitInactiveDays` (0 = off; fractions allowed)
- **Client TOML:** `hud.enabled`, `input.dashDoubleTapMillis` (§3.22),
  `visuals.firstPersonAnimations`, `visuals.animationFades`, `visuals.vfxQuality`, and for the roll reveal (§3.12)
  `reveal.animation` (scenes on/off), `reveal.alwaysFull`, `reveal.reducedMotion`, `reveal.fakeOutChance` (0.2),
  `reveal.debugForceFakeOut` and `reveal.seenTechniques`, and `impact` (§3.23: shake, hit-stop, impact frames and each
  tier's look). All but `hud.enabled`, `reveal.fakeOutChance`, `reveal.debugForceFakeOut`, `reveal.seenTechniques` and
  `impact` are also on the Sorcerer screen's Settings page (§3.12), which saves them at once; of `impact`, the shake
  strength and impact frames are there too.
- Both are editable in-game via Mods → Kegare → Config. Labels are generated into the lang file.
- **Migrations (`KegareConfigMigration`).** NeoForge keeps every value in an existing file and only adds missing keys, so a changed
  default never reaches a file that already exists. `kegare-server.toml` has a `configVersion` (a file without one reads as 1). On load, a
  file behind `CURRENT_VERSION` is fixed once: a value still at its old default moves to the new one, and a value that's neither was changed
  by hand, so it stays and the server log lists it. **Version 2** is the Malice rescale (the tiers, and every cost and upkeep x4). It doesn't
  touch players' saved data, so anyone already born keeps the capacity they rolled. **Version 3** is the stronger Severed melee numbers.
  **Version 4** is the Impact System's Malice input (§3.23): its re-tuned weights and tiers, and battle damage's `strengthScale`,
  `radiusPerStrength` and slams' `strengthPerSpeed` with them (§3.24). A later change to a shipped default that needs the same
  treatment adds its own table and bumps `CURRENT_VERSION`.

### 3.10 Data generation and art
- `./gradlew runData` generates lang, the item model, tags (`kegare:talismans`), the talisman recipe
  (gold + amethyst + paper; overridable by datapack) and the advancements.
- `python3 tools/gen_art.py [--preview sheet.png]` regenerates all GUI and item art (needs Pillow). The art is
  procedural but drawn to look hand-pixelled. `--preview` also writes a contact sheet of every asset at 4×.
  - **Direction ("defiled ink"):** blackened cursed-iron frames lit from the top-left with a violet rim, smoky
    plum-black ink surfaces, Malice violet, ofuda paper and a red seal as accents. Techniques used: a 1px near-black
    ink outline on everything, ordered (Bayer) dithering between hand-picked color ramps, mottled metal, rim light,
    and tapered brush strokes with wobble and dry-brush gaps.
  - **Every asset is original,** and no third-party file is in this repo.
  - **Nine-slice sprites** (`textures/gui/sprites/`, each with a `.mcmeta`): `panel`,
    `tab`/`tab_selected`, `button`/`button_highlighted`/`button_disabled`
    (drawn by `InkButton`, a vanilla button with Kegare's sprites), and `divider` (a brush stroke, 3-slice).
    In 1.21.1 the edges and centre **tile**, they do not stretch, so the generator makes them seamless along the
    tile period and keeps every ornament inside the corners.
  - **Plain sprites:** `sparkle`, `severed_emblem`, and the roll reveal's in `sprites/reveal/`: `talisman`, `flame_0`-`7`
    (a looping flame), `eye_0`-`5` (an eye opening), `glow`, `ring`, `ray`, `star`, `star_small`, `ash`.
    The flames, glow, ring, ray and stars are greyscale, tinted in code by rarity.
  - **Textures:** the talisman item, `gui/malice_bar.png`, the combat panel's `gui/combat/*`, and
    `gui/reveal_bg.png` (128×128 seamless smoke, tiled behind the reveal by `GuiDraw.inkBackground`).
    - `malice_bar.png` is 32×30: rows 0–9 the empty bar, rows 10–19 the fill's shading in greyscale, rows 20–29 a
      white shine; 5px caps, a 22px middle that tiles. `GuiDraw.maliceBar` draws it for both the HUD and the
      Sorcerer screen, tinting the fill with the innate technique's Malice color (§3.3) and drawing the shine
      untinted on top, so any color keeps its gloss and stays readable.
- **Sounds** (Kegare's own, no recordings): `python3 tools/sounds/build.py` synthesizes them from seeded noise and tones
  (plain Python, written as mono Vorbis `.ogg` through the system's libsndfile, so they're positional) into
  `assets/kegare/sounds/<technique>/`; `--preview` also writes the candidates to `run/sounds_preview/`. Each one is
  registered in `sound/KegareSounds` (event `kegare:<technique>.<name>`, its file and its subtitle key); runData writes
  `sounds.json` from that list (`KegareSoundProvider`) and the subtitle goes in the language provider. `SoundsTest`
  checks every registered sound has a mono file, a subtitle and an entry, and no file is left unused. A new sound: a
  function in the technique's `tools/sounds/<technique>.py`, an entry in `KegareSounds.ALL`, its subtitle, then
  `build.py` and runData. The writer gives every file a fixed stream serial (libsndfile picks a random one), so a
  rebuild of an unchanged sound is the same bytes and only changed sounds show in git.
- **Art for content (optional, with fallbacks).** New content should ship with:
  - an **emblem** per innate technique: `<namespace>:textures/gui/emblem/<path>.png`, 48×48. It is shown
    on the reveal's name card, the Sorcerer screen and the talisman prompt. Without one, the tab icon item is drawn instead.
  - an **icon** per ability: `<namespace>:textures/gui/ability/<path>.png`, 16×16. It is shown in the combat
    panel's slots and the Sorcerer screen. Without one, the slot number is drawn instead.
  - Whether the art exists is looked up once per texture, and the answer is forgotten on resource reload, so
    resource packs can add or replace it.

### 3.11 Advancements and tabs
All advancements use `minecraft:impossible` and are granted from code (`KegareAdvancements.award`).
Each tab has its own root.

**Base tab** (root `awakening`):

| Advancement | Frame | Visible before earned? | When |
|---|---|---|---|
| *Awakening* (root) | task | yes | born |
| *Reawakening* | task | yes | used a Purification Talisman |
| *Chosen by Fate* | challenge | yes, **silent** (reveals a Legendary roll) | rolled a Legendary |
| *Bitter Luck* (under Reawakening) | goal | hidden | hit hard pity |
| *Severed* | goal | hidden | born with 0 Malice |
| *Overflowing* | goal | hidden, **silent** (reveals Malice capacity) | born (or reborn) in the Vast tier |
| *Running on Empty* | task | yes | visible Malice (floored, like the HUD) drops to 0 while in combat |
| *A Green Light* | goal | hidden, **silent** (reveals a player can heal) | unlocked Reverse Malice Technique (took in the green orb, §3.18) |
| *It's been a while, huh?* (under A Green Light) | challenge | hidden, **silent** | started a Reverse Malice Technique cast at 6 HP or less, within 10 s of being hit by a player |
| *Moving Up* | task | hidden, **silent** (Grade is private, §3.21) | reached Grade 3 |
| *Proven* | goal | hidden, **silent** | reached Grade 2 |
| *Recognized* | challenge | hidden, **silent** | reached Grade 1 |
| *Outside the Ladder* | challenge | hidden, **silent** | reached Special Grade |
| *Full Kit* | goal | hidden, **silent** | Refinement reached the level that unlocks every ability and special of the current technique (the ultimate doesn't count) |

**Six Eyes tab** (root `clear_sight`). Everything here is **silent**, and every advancement except the root is
**hidden** (secret-identity rule and its visible-root exception, §1):

| Advancement | Frame | When |
|---|---|---|
| *Clear Sight* (root, **visible**) | challenge | born with it |
| *The Cycle Continues* | challenge | inherited it |
| *Eyes Closed* | task | lost it |
| *Blinded* | goal | killed a bearer |
| *Something's Missing* | goal | a full-detail Read of a Severed player (§3.32) |

**Rule: every innate technique gets its own tab, whose root unlocks the first time the player rolls it.**
- It's automatic. Datagen generates the root `kegare:innate_technique/<path>` for every non-test innate technique:
  - title: its name, in rarity color
  - icon: `InnateTechnique.Builder.tabIcon(...)`, default an enchanted book
  - background: black concrete
- Every roll (birth, talisman, admin, replacement) awards it; later rolls are no-ops. `/kegare innate set`
  is not a roll and doesn't award it.
- Give that innate technique's own advancements this root as their parent.
- The root is **silent in chat**. Announcing it would tell every opponent which innate technique a player rolled. The
  same goes for everything in the tab: datagen fails if any advancement under `innate_technique/` announces.
- Test innate techniques get no tab.
- Tabs so far: Rime (§3.14), Swap (§3.19).

**Who sees which tab:** vanilla only shows a tab once the player has earned something in it.
- Everyone sees the Base tab (*Awakening* is granted at birth).
- The Six Eyes tab appears for whoever has earned one of its advancements: a born or inheriting holder, a
  former holder (*Eyes Closed*), or a killer (*Blinded*). Uninvolved players never see it. An admin-granted holder
  has earned nothing there, so it stays hidden for them until something happens.
- Because *Clear Sight* is visible, involved players who weren't born with the eyes see it as an unearned (grey)
  root, with their own advancement linked to it. (A hidden root would not be drawn at all.)

### 3.12 GUIs (`client.gui`)
**Rule: results are decided and saved on the SERVER before any screen opens.** Screens are cosmetic and never send
a result back; they only send requests the server re-validates. All text comes from the lang file.

| Screen | Opens when | Data | Sends |
|---|---|---|---|
| Roll reveal (`RevealScreen`, `RevealScript`, `RevealLayout`) | the server finished a roll: Awakening, Reawakening, admin reroll, replacement | `RevealPayload`, sent only to that player | nothing |
| Sorcerer (`SorcererScreen`) | key **K** | `SorcererInfoPayload`, computed by the server, plus the live sync (loadout, Malice, cooldowns) | the open request (again whenever the sync shows an unlock, reroll or trait change); loadout edit requests (§3.16) |
| Talisman confirm (`TalismanConfirmScreen`) | using a Purification Talisman (nothing consumed yet) | `TalismanPromptPayload` | a confirm request |

**Roll reveal** (`RevealScreen` draws it. `RevealScript` holds the timeline and `RevealLayout` the sizes, both plain Java and
unit-tested.)

A cinematic run of scenes, longer the rarer the result. The result was decided and saved before the screen opened, so
closing it or disconnecting at any point changes nothing.

| Rarity | Length | Scenes |
|---|---|---|
| Common | ~3s | Omen, Rarity, Name |
| Rare | ~5s | Omen, Rarity, Stars, Name |
| Epic | ~7s | Omen, Rarity, Stars, Epithet, Name |
| Legendary | ~10s | Omen, Rarity, Stars, Epithet, Name, with a screen flash, gold light rays and the fanfare |

- **Omen:** a talisman burns in the middle of a dark screen. The flame's color hints at the rarity: grey, blue, purple, gold.
  **Fake-out:** on a Legendary, a `reveal.fakeOutChance` chance (20%) that the flame starts purple and flares to gold
  halfway through. `reveal.debugForceFakeOut` forces it, for testing.
- **Rarity:** the rarity word slams in, in rarity color.
- **Stars:** 1 to 4 stars (Common 1, Rare 2, Epic 3, Legendary 4) drop in one at a time, with a chime each. Common has no
  Stars scene, so its star is only on the name card's row.
- **Epithet** (§3.3): typed out slowly on a dark background.
- **Name:** the name large, across the emblem, with particles in the technique's Malice color. The stars and rarity, the
  one-line `.desc` and the ability icons then fade in. `RevealLayout.rowStep` closes the icon row up as needed, so 1 to 9
  abilities fit at every GUI scale.
  - **The player model** stands beside the emblem, playing the technique's signature animation (§3.3) every few seconds. PAL works
    in a GUI because it hooks the player's tick and renderer, not the world pass, so this is the real local player, client-only, and
    it stops when the card goes away. `RevealScreen.renderModel` copies vanilla's GUI entity call but passes the real partial tick
    (vanilla passes 1, which steps PAL's animation at 20 fps).
- **Birth reveals** add a **Malice** scene after the name: the capacity counts up (up to 5 digits) and the tier lands. Both stay
  on the end card.
- **Severed:** the talisman burns out to grey ash, then "Heaven Gave You Nothing", then "Born without Malice". Always the same.
- **Six Eyes** (a birth trait) adds a scene after the technique: a blue eye opens, "Nothing Is Hidden From You", then "Only you know
  this." The end card repeats those two lines and doesn't name the trait. Other birth traits get a line on the end card. All of it
  is shown only to that player and never broadcast.
- **Short version:** the first time this client rolls a technique, the full reveal plays. Later rolls of that technique play Rarity
  then Name, and keep a Legendary's flash, rays and fanfare. The seen list is client-side (`reveal.seenTechniques`), so it's per
  install, not per player. `reveal.alwaysFull` plays the full reveal every time. Birth's Malice scene and the Six Eyes scene still play
  on the short version.
- **Skip:** Esc, Space, Enter or a click jumps to the end card; again closes. There are no buttons. A press within 280ms of the
  screen opening or the end being reached is ignored, so a double-press can't throw the result away unseen.
- `reveal.animation=false` shows the end card at once.
- **Reduced motion:** `reveal.reducedMotion` (on the Settings page), or vanilla's Hide Lightning Flashes, tones the flashes down to
  15%, turns the shake off and stops the rays turning.
- **Sound:** every cue is a UI sound on the roller's client (`SimpleSoundInstance.forUI`), so nobody in the world hears it. They're
  all vanilla sounds. The server plays no sound for a roll, a Legendary's included.
- **Layout:** the scenes are drawn on a canvas at a whole-number multiple of GUI units (`RevealLayout.canvasScale`), never smaller than
  320x240, so they look the same at every GUI scale and only have to fit 320x240.
- **No spoilers:** the background is opaque, so chat and HUD stay hidden. Toasts such as *Chosen by Fate* are held until the reveal
  closes.
- Reveals queue up and open only when no other screen is open, e.g. after the world finishes loading on first join.

**Sorcerer screen** (one window)
- **Frame:** a riveted plum nine-slice (`menu_frame`) with dark inset wells (`menu_well`) inside it.
- **Left edge:** ability category tabs (`menu_tab`): Innate, Malice and Melee, each with its own icon (§3.16).
- **Right edge:** view buttons: Innate Technique, Background (a loop, §3.31), Progress (rising bars), Traits (an eye), Pity (a star) and Settings.
- **Header:** the framed emblem, the name in rarity color, the epithet (§3.3), "rarity · category", then the selected category's
  abilities as tiles (the HUD's slot frames). A gold number marks the slot each tile is on, and locked shared
  abilities show a padlock. A technique ability that Refinement hasn't reached is a greyed tile with a padlock and its
  required level; it can't be picked up (§3.21).
- **Details box** (the large well) shows whatever ability is hovered (a tile or a bar slot). Clicking a tile keeps
  it there. It lists:
  - category and cast type;
  - current cost, upkeep and cooldown, plus the surroundings' cost factors (innate technique abilities only);
  - the description;
  - the special block (§3.15);
  - where it sits on the bar.

  With nothing hovered, it shows the technique's description and how to edit the bar. Locked shared abilities show
  "???". A locked technique ability or special keeps its name and text, greyed, with a padlock and "Requires Refinement X."
  in red, so a player can read what they're working toward. The mouse wheel scrolls the box when the text is taller than it, with a thin scrollbar. The box also holds
  the Progress view (below), the Traits view (name, a unique tag, description), the Pity view and the Settings view:
  - the count, with a progress bar toward hard pity
  - "Soft pity starts in N rolls", or the active Legendary weight
  - "Legendary guaranteed in N rolls" (`PityRoller.rollsUntilSoftPity` / `rollsUntilHardPity`, unit-tested)
  - total rolls
  - **Settings** (a gear): client options as button rows, the current value lit gold, saved to the client config
    at once: ability effects
    (Full / Reduced / Vanilla), your own animations in first person, the roll reveal animation, always playing the full
    reveal, and reduced motion in the reveal. Screen shake (§3.23) is a slider instead: drag or click along its track,
    0 to 200% in steps of 5% (a notch marks 100%), saved when it's let go. Impact frames (§3.23) are an On / Off row,
    since a whole-screen flash can bother some people.
- **Right column:** the player model (follows the mouse), Malice current / capacity with the bar in the technique's
  Malice color, the tier, and regen per second (or "Regen paused"). In a window too narrow for them (640x480), the amount and
  "Regen paused" each take a second line and the model gives up the height; shrinking them would land the font on fractions of a
  pixel and close up the zeros.
- **Bottom:** the HUD's combat panel itself (`CombatPanelLayer.drawPanel`), live, as the loadout bar (§3.16). Above
  it is a status line (hint, "Now click a slot on your bar", or the server's refusal), with "Reset" at its right end. The line is
  centered on the panel while that clears Reset, and centered in the space left of Reset when it doesn't.
- **Severed:** the Severed emblem and text, no category tabs and no bar.
- **Progress view** (§3.21): the Grade name, an XP bar to the next step, and the current Assessment against its requirement where
  one applies (average, Technique use (Melee for a Severed player), fights, opponents, Peak Refinement; each turns green when met, and at Grade 1 the XP line gives way to
  Assessment alone). Then the current technique's Refinement level and bar, Peak Refinement, and the three Insight values. It scrolls in
  small windows like the rest of the box.
- **Severed** players still get Progress (no Refinement or Peak Refinement), Traits, Pity and Settings.
- **Keys:** 1–6 or Tab switch views, K or Esc close.

**Talisman confirm:** *"Reroll your Innate Technique? Current: X. Pity: Y/50."*, with the current emblem.
- **Reroll** sends a request. The server re-checks that the talisman is still in that hand, combat and Severed
  status, then rolls, consumes one talisman and sends the reveal.
- **Cancel** or Esc consumes nothing.
- Using the talisman while Severed or in combat is refused before the screen even opens.

**Layout and testing**
- Layouts are computed from the screen size and support GUI sizes down to Minecraft's minimum of 320×240.
- Every screen fits at GUI scales 1–4 on a 1920×1080 window, and in a 640×480 window (auto scale, which gives a 320×240 GUI).

### 3.13 Animations and VFX (visual only)
**Rule: visuals are cosmetic. The server acts first and never waits on an animation or an effect.**

- **Libraries:** player animations use Player Animation Library (PAL, by ZigyTheBird). VFX use Photon (by
  KilaBash), which needs LDLib2. All three are required mods; see README.
- **Declaring:** `Ability.visuals()` returns `AbilityVisuals`, which can set a PAL animation ID and/or a Photon effect
  ID for each `VisualPhase`:

  | Phase | When | Plays |
  |---|---|---|
  | `CAST` | INSTANT fired, CHANNELED started | once |
  | `CHARGE_LOOP` | while charging | loop; the effect grows from 30% to full size over the full charge time |
  | `RELEASE` | CHARGED fired (a too-short tap fizzles and shows nothing) | once |
  | `CHANNEL_LOOP` | while channeling | loop |
  | `TOGGLE_ON` / `TOGGLE_OFF` | toggle switched on / off | once |
  | `TOGGLE_LOOP` | while toggled on | loop |
  | `PROJECTILE_TRAIL` | on the ability's projectile entity | loop, started by the projectile on the client |
  | `IMPACT` | where it hits | once, at a position |

  Each effect has an anchor on its entity: `EYES` (turns with the look), `BODY`, `FEET`, or `MOTION`
  (projectiles). Photon turns the effect so its local +X axis points forward, so effects are authored facing +X.
- **Files:** animations go in `assets/<ns>/player_animations/*.json` (Blockbench/GeckoLib format). The animation's
  ID is the namespace plus the name inside the file. Effects go in `assets/<ns>/fx/<path>.fx`, with ID `<ns>:<path>`.
- **Networking:** `CastManager` calls `VisualService` at each start and end point. The service sends one
  `VisualPayload` (play once, start or stop a keyed loop, stop all, play at a position) to the caster and everyone
  tracking them. Impacts go to players within 64 blocks.
- **Late viewers:** loops are remembered per entity (runtime attachment `kegare:visual_state`) and sent to players who
  start tracking it later, with how long each has been running, so they see it where everyone else does (§3.5). So a
  visible loop always means the thing it shows is active.
- **Stopping:** a charge or channel ending for any reason (release, out of Malice, max duration, stun or freeze,
  death, logout) stops its loop. Toggles keep running while stunned, so their loop stays too. A toggle switched off
  stops its loop and plays `TOGGLE_OFF`. Death, logout and a dimension change stop everything on the entity. **A
  dimension change ends charges, channels and toggles** (`EndReason.DIMENSION_CHANGE`).
- **What ends, vanishes:** when a loop stops, or its entity is gone, its effect is removed at once. A shell, cone or
  charge must never linger after it ends (a lingering shell would mislead opponents). Only projectile trails fade
  out behind their projectile.
- **Effects a move draws itself:** `ClientVisuals.drawnByMove(effect)` keeps a loop of it keyed and timed as usual, and
  still tells the listeners of a one-shot, but plays neither Photon nor vanilla particles for it (nor preloads it); the
  move finds it through a `ClientVisuals.Listener` (`loopStarted`, `loopStopped`, `playedOnce`) and `loopTime`.
  Switchback's countdown ring, Mimic's flicker and Momentum Exchange's streaks are such effects (§3.19).
- **Nothing in front of your own eyes:** an effect at a position closer than 2 blocks to a first-person camera
  (you got hit, you broke free) is skipped. Even small particles there would cover the screen; you still get the
  hurt flash, overlays, HUD and sound. Your own entity-attached loops are authored away from the camera: Rime's
  charge sits a block ahead, the cone starts in front of you, and the shell is invisible from inside. Your own effect
  particles (vanilla's swirls for Slowness, Speed and the rest) aren't spawned while you're in first person
  (`OwnEffectParticlesMixin`): they rise round your body, so they would drift across your view, and Rime's Slowness would make a cloud
  of pale blue swirls in the middle of a fight. Everyone else still sees yours, since they show who's slowed, and so do you
  in third person.
- **Near the camera:** a positional effect closer than 2 blocks to a first-person camera isn't drawn, or it would sit in front of your eyes. `ClientVisuals.setNearCameraDistance` lowers that for one effect (Reinforced Strike's impact, 1 block: only the target is that close).
- **On your own screen:** `ClientVisuals.setFirstPersonVariant` swaps an effect riding a player for a quieter one, for that player in first person only (the dash's trail, the parry's spark and the guard's hit).
- **Your own hands** (`PlayerAnimations`). In your own first person an animation can show your arms (PAL's first-person
  model), or leave the hands to vanilla. Everyone else always sees the whole animation. Nothing may fill the middle of the
  view, so:
  - Holding anything in either hand (a sword, an axe, a shield, a block), every animation leaves the hands to vanilla.
    PAL's model draws what's held at its real size right by the camera, usually edge on, so a cast would swing a dark blade or
    a shield's back through the view. Only an empty-handed cast shows its gesture.
  - `keepVanillaHands`: never shown. Melee's animations, every Rime cast, Swap's Mimic, and Puppet Manipulation's way back
    and Zip.
  - `handsWhileLevel`: shown only while you look no more than 15° down. The arms hang from the body, which doesn't tip
    with the view, so hands at chest height sit at the bottom corners of a level view and come up into its middle as you
    look down. Every other Swap and Puppet Manipulation cast. Looking up takes them out of view.
  - Rime's `frozen` is the one on neither list: you can't move, and your arms stay where they are.
  - While PAL draws your own arms for your first-person view (`PlayerAnimations.firstPersonPass`), the layers drawn on a
    player's body skip it: Freeze's frost, the Rime Shell's plates and a possessor's glow. PAL hides the head and body
    there, but a layer draws its own copy of the parts and would put them round the camera.
- **Failures never crash:** a missing or broken `.fx` falls back to vanilla particles (`VanillaFallback`, per-effect
  lookalikes), and a missing animation is skipped. Each one is logged once. Effects are preloaded at client setup.
- **Client config (`visuals`):**
  - `firstPersonAnimations` (default on): your own arms animate in first person (PAL `THIRD_PERSON_MODEL` mode), within
    the rules under "Your own hands" above.
  - `animationFades` (default on): see below. It's per viewer: it changes how YOU see everyone's animations.
- **Fades are in code, not in the files** (`PlayerAnimations`), because a Blockbench export can't carry them, and every
  animation gets them: a 3-tick blend through PAL's fade modifiers. It starts from the animation being replaced if there is
  one, else from the vanilla pose. A play-once blends back to the vanilla pose over its last 3 ticks. A loop, or anything stopped
  part way, blends from the pose it's in to an empty animation (`thenWait`). Files therefore declare no `beginTick`/`endTick`
  (`PuppetAnimationsTest` fails if one does): that would blend twice with fades on, and still blend with them off. Animations
  should start and end on rest keys, so that with fades off they never jump to a mid-pose. Channels an animation doesn't key
  keep the vanilla pose throughout.
  - `vfxQuality`: `FULL` (Photon), `REDUCED` (Photon, emitters at half rate and half particle cap) or `VANILLA`
    (vanilla particles only).
- Network version: see §3.5 (the one place it is kept).

### 3.15 Specials (R)
- Any slot ability can define a **special** (`Ability.special()`): a second ability cast with **R** while the base is
  selected. Build it on `SpecialAbility(id, castType, () -> base, requirements...)`. It has its own:
  - cast type (INSTANT / CHARGED / CHANNELED / TOGGLE; hold R for CHARGED and CHANNELED, press R again to switch a
    TOGGLE special off),
  - Malice cost and upkeep, effect (`execute`/`tick`/`onEnd`), and visuals (animation and VFX IDs per phase, §3.13),
  - lang name and description (`ability.kegare.<id>`, `.desc`).
- **Rule: every special has a TELL.** A distinct, readable animation, VFX or sound that other players can see or
  hear when it is cast, so opponents can learn to react. "Distinct" means telling it apart from its base ability (and
  the technique's other abilities) at the moment it goes off, not only afterwards. Private cues (an effect only the
  caster sees) don't count.

  | Special (base) | Tell |
  |---|---|
  | Splinter (Frost Shard) | own cast animation (a flat backhand sweep, not Frost Shard's overhand flick) and a fan of glints, three shards in a fan, a brighter crack (amethyst break) |
  | Glacial Spire (Glacial Lance) | the fist raised, gathering cold; a glowing pixel crack ringing the spot with bright glints streaking up from its edge for 0.75 s before the spike |
  | Ice Path (Frost Field) | own sliding pose, an ice trail left behind, glass sounds |
  | Shatter Shell (Rime Shell) | own cast animation, an icy burst, glass and amethyst shattering |
  | Switchback (Positions) | a double clap, seen and heard: its own animation (`switchback_cast`: two claps, then the right hand turned back to the chest) and sound (`swap.double_clap`, at both ends), and the countdown rings go up on both as it's cast |
  | Mimic (Awareness) | its own cupped clap up by the face (animation and `swap.cupped_clap`), and the caster's whole body flashing teal twice (`mimic_flicker`), which everyone nearby sees; the trick is the disguise afterwards, not a hidden cast |
  | Send Off (Anchor) | a clap and its own two-handed shove (`send_off_cast`, both palms pushed out at the target), with a rush of air heard at the caster (`swap.shove`); the target is gone along a teal line onto the token, a lower clap at both ends |
  | Momentum Exchange (Exchange) | its own hard clap thrown forward, then the arms flung back behind (`momentum_cast`), heard low (the clap at pitch 0.8, at both); a teal ring snaps round both waists and speed lines trail each along the way they're sent |
  | Possess (Puppet Creation) | the puppet jolts awake, arms flung wide (`possess_cast`), a soul-escape sound at the body and a lavender thread shooting to the puppet; afterwards the empty body stands slack, a thread running from it to the puppet |
  | Focus (Directive) | own wind-up and a hard point at the target, held, the other hand yanked back (`focus_point`); a bell at the target and a lavender mark on it for 2 s (a ring tightening round it, a bead over its head) |
  | Chain Burst (Curio Burst) | own cast: hands gathered, flung up into a wide Y, then slammed down and out (`chain_burst_cast`); a rising whistle at the target, then the blasts going off one after another |
  | Stand-In (Understudy) | own stage bow, then a hand presenting the double (`stand_in_cast`); the puppet grows inside a rising column of lavender threads with a mirror sound (and shrinks back the same way) |
  | Zip (Strings, R) | yanked off the ground: the string arm up and ahead, body and legs trailing behind it (`strings_zip`); the string runs taut and shimmers, and YOU are the one moving, with a bobber reel at a higher pitch than Reel In's |
  | Leash (Strings, R) | two leads in two fists: yanked back low and wide, leaning back, held (`strings_leash`); a second string shoots from the caster and a knot grips the second target, and two taut strings run from the slowed caster for 5 s |

  Strings' base casts have tells of their own too, because the string itself is the tell:

  | Base cast | Tell |
  |---|---|
  | Strings, firing | one hand cocked back and thrown straight out (`strings_fire`), a bobber throw; the string shoots from the hand in 3 ticks, and its knot grips with a burst of fibers (`strings_attach`) and a leash-knot sound. Anyone can see who is holding a string on whom, and that it's waiting: it hangs slack |
  | Reel In | hand over hand, leaning back against the weight (`strings_reel`); the string snaps straight and shimmers (`strings_tension`), a low bobber reel at the target |
  | Tie | arms flung wide, then slammed together until the wrists cross (`strings_tie`); the string jumps to run between the two targets, not from the caster; a thud and fibers when they meet |
  | A string snapping or running out | fibers flung from both ends and the middle (`strings_snap`), and a leash-knot break if it snapped |
- **Shared cooldown:** `cooldownKey()` is the base ability's ID, so casting either the base or the special starts the
  one cooldown and both show it on the base slot. The length defaults to the base's `cooldownTicks` (a special may
  override it).
- **Server pipeline** (`CastManager`): R with a number key, or R alone, sends `SPECIAL_PRESS`/`SPECIAL_RELEASE` (§3.5). The server resolves the selected
  ability, then its special:
  - no special → `"<ability> has no special."`, nothing paid;
  - otherwise the same shared checks as a base cast (busy, stun, cooldown, requirements, cost, `canCast`), and the
    same lifecycle. Only `SPECIAL_RELEASE` ends a special's charge/channel, and the client sends it when the number key comes up.
- **Hooks specials use:** `Ability.canRelease(ctx)` (CHARGED: checked at release before paying; false fizzles
  for free with `blockedMessage`), `CastManager.switchOff(player, toggle, reason)` (end a toggle from code, e.g.
  `EndReason.CONSUMED`), and lingering visual loops (§3.14, Ice Path).
- **Requirements** (`Requirement`): `Requirement.trait(trait)` (said as "a rare trait", never by name, §1), `Requirement.toggleActive(ability)` or
  `Requirement.of(test, description)`.
  - Unmet at the press → `"<special> requires <description>."`, nothing paid, no cooldown.
  - Re-checked at a charge's release (a lapse fizzles for free). A channel or toggle ends when one lapses.
- **Sorcerer screen:** in an ability's details, an **R** badge with "Special: name (type) · cost" (gold when
  available now, grey when a requirement is unmet) or "No special", then the special's description and its
  requirements (green met / red unmet).
- **HUD:** action-bar messages (cast feedback) and the held item's name move up to clear the combat panel
  (`HudClearance`). The panel's R badge marks slots whose ability has a special. A special's charge/channel outlines its
  base slot, and a TOGGLE special lights the base slot green.
- **Tests:** `SpecialsTest` (in-game JUnit) covers fizzles without cost, both requirement kinds, the release
  re-check and the shared cooldown both ways.

### 3.16 Loadout and ability categories
Package `loadout`. Abilities are sorted into category tabs, and a
separate bar is filled from any of them.
- **Categories** (`AbilityCategory`), one tab each on the Sorcerer screen's left edge:
  - **Innate Technique**: the current innate technique's abilities. A reroll replaces them.
  - **Shared**: abilities a player unlocks once and keeps through every reroll (`SharedAbilities` registry,
    unlocks in attachment `kegare:shared_abilities`, saved, kept on death). Reverse Malice Technique is the first
    (§3.17). Later categories (martial arts, cursed tools...) slot in as more enum values.
- **The loadout** (attachment `kegare:loadout`, saved, kept on death; `LoadoutService`):
  - **nine** regular slots (`LoadoutService.SLOTS`, number keys 1–9). By default the abilities the player has unlocked
    (§3.21; at Refinement 0, the first two) fill the first ones in order and the rest stay empty, ready for later
    unlocks, shared abilities (Reverse Malice Technique) and whatever comes later;
  - **a new unlock goes into the first empty slot,** if there is one (`LoadoutService.offer`). If the bar is full it just
    becomes available to place;
  - **lowering Refinement** (an admin command) takes newly locked abilities off the bar and stops them
    (`LoadoutService.removeLocked`). The slots are left empty, and a later unlock offers them a slot again;
  - bars saved before there were nine slots (one per ability) keep their order and are padded on login;
  - each slot holds one of those abilities, an unlocked shared ability, or nothing ("Empty slot"; casting it says
    so and costs nothing);
  - nothing is slotted twice: placing an ability that is already on the bar moves it (whatever was in the target
    goes where it came from), so a technique ability taken off the bar can always be put back;
  - the ultimate (V) is **not** a loadout slot and can never change;
  - changing the innate technique (reroll, admin, rebirth) resets the loadout to the new technique's level 0 kit; shared
    unlocks stay, unlocked but off the bar, and Refinement doesn't gate them;
  - on login a layout built for another technique (or the wrong size) is rebuilt, and entries that no longer
    resolve (locked again, removed by an update) or repeat are emptied.
- **Everything reads the loadout**, never the technique's fixed list: number keys and R (`CastManager` resolves the
  selected loadout slot; specials come from whatever is slotted), Technique Mode, the HUD
  combat panel, the Sorcerer screen and `/kegare info`.
- **Editing** (Sorcerer screen, §3.12):
  - category tabs on the left edge (the innate technique's emblem; a silver ring for Shared). Locked shared
    abilities show a padlock and "???".
  - the selected category's abilities as tiles in the header (a gold number marks the slot each is on). Their
    details fill the large box.
  - the loadout bar is the HUD's combat panel, drawn live: slot keys, R badges, cooldowns and the fixed ultimate
    (a padlock while locked).
  - drag a tile onto a slot, or click a tile then a slot. Drag a slot onto another to swap. Drag one off the bar
    or right-click it to empty it. "Reset" restores the default. The slot under a drag is outlined white.
- **Server validation** (`LoadoutService.edit`, every request; the client is never trusted):
  - not Severed and has an innate technique;
  - a real regular slot (the ultimate's position → "The ultimate slot can't be changed.");
  - **not in combat** ("You can't change your loadout mid-fight.") and not mid-cast ("Finish casting first.");
  - the ability belongs to the current innate technique and Refinement has reached it (§3.21), or is a shared ability the
    player has **unlocked** ("You haven't unlocked that ability.");
  - no duplicates.

  A refusal shows on the action bar and on the Sorcerer screen's status line (`LoadoutResultPayload`). A toggle
  taken off the bar switches off. The sync carries the loadout, the unlocked shared abilities and whether the
  player is in combat (re-checked every 10 ticks), so the screen and HUD update live.
- **Commands:** `/kegare debug shared unlock|lock <player> <ability>`, `/kegare loadout reset [player]`; `/kegare info`
  lists the loadout and the unlocked shared abilities.
- **Tests:** `LoadoutTest` (in-game JUnit): default layout, moving instead of duplicating, empty slots, the ultimate
  and bad slots, other techniques' abilities, mid-cast and in-combat refusals, toggles switching off, reset on a new
  technique, login repair.

- **New abilities reach existing bars once** (`LoadoutData.known`): on login, an ability the technique gained after the bar
  was built goes in its default slot if that's free, else the first free one. If the player then clears it, it stays
  cleared.

### 3.17 Reverse Malice Technique (RMT)
Package `rmt`. The first **shared** ability (§3.16), ID `kegare:reverse_malice_technique`. Numbers in
`[reverse_malice_technique]` of `kegare-server.toml`. Malice is negative energy, and this multiplies it by itself: negative times
negative is positive energy, which is why it heals, and why its colors are white and green.
- **Locked by default.** Found through the green orb (§3.18); `/kegare debug shared unlock|lock` for admins. Severed
  players can never unlock it (`SharedAbilityService.unlock` refuses) or cast it (the cast pipeline refuses Severed
  players for everything).
- **CHANNELED:** hold its number key to heal **2 HP** at the end of every
  full second held (`healPerSecond`); release to stop. Never above max health; once there is nothing left to heal
  the channel ends by itself ("Fully healed."). At full health it is refused before anything is paid ("You aren't
  hurt.").
- **Expensive:** 40 Malice to start, then **96 Malice/s**, about double a typical attack's cost. Shared abilities take
  no innate technique's surroundings modifier.
- **Ends** like every channel: release, out of Malice, `maxDuration` (0 = none), a stun or a freeze (interrupted);
  plus fully healed. The **15 s cooldown** starts when it ends.
- **No special:** R on it fizzles at no cost.
- **Visuals:** Photon only; **it has no player animation**, so the caster's body doesn't move. `rmt/rmt_channel_aura` (green and

### 3.18 The green orb (unlocking RMT)
`rmt.GreenOrbService` (server) and `rmt.client.GreenOrbClient`. Numbers in `[reverse_malice_technique.orb]`.
- **When:** a real hit **from another player** that leaves someone at **10 HP (5 hearts) or less**
  (`healthThreshold`) rolls a **15%** chance (`chance`). At most **one roll per 60 s** per player (`rollCooldown`; the
  roll counts whether or not the orb comes; last roll saved in `kegare:shared_abilities`). Only for players who
  are born, **not Severed**, haven't unlocked RMT, and have no orb waiting.
- **Where:** the server rolls a **route**. It starts **3 blocks** in front of the eyes (`distance`), **25° to the left or right**
  of the crosshair (`sideAngle`, random side: clearly in view, but taking it in is a choice, never an accident while
  staring at an opponent), at half the look's pitch so it stays near eye level. From there it's a random walk over the view (`rmt.OrbPath`):
  **5 steps** (`pathLegs`) of **18°** (`pathStep`), turning between 40° and 120° each time (`pathMaxTurn`), never further than **45°** left or
  right (`pathYawRange`) or **25°** up or down (`pathPitchRange`) of where they were looking, every point short of any wall in the way, with a smooth
  curve through the points. It sends the route **to that player only** (`OrbPayload`); no other player is told anything. The orb is client-side:
  green with a white heart, breathing and drifting a little, in a soft halo with circling motes (`rmt/rmt_orb`), with **faint dots marking the way
  ahead** (`rmt/rmt_trail_dot`) and sparks left hanging behind it (vanilla stand-in: green dust and happy-villager sparkles, white dust for the dots), and a soft
  chime. It **fades after 5 s** (`lifetime`), not counting time spent following it, so a follow under way can't fade; the server says when.
- **Taking it in: follow it to the end.** Each tick the server checks the player's look against where the orb is now (within `lookAngle`,
  10°). While it's in sight it moves on along the route, and the route takes **3 s** (`followSeconds`), so about **30°/s** to track; the dots go out as it passes them.
  Out of sight, it runs back **3× as fast** (`followRewind`), and the dots come back. So looking at it without moving gets nowhere: it wanders off to the edge of
  the look and hovers there. Losing it isn't final: catch it again and it carries on from there, or run it from the start while time remains. High ping makes the
  orb move slower rather than fail, since it only moves on when the server sees the look on it. The server sends the progress every tick it changes, and the client only draws
  it, swelling it as it nears the end. A new route is rolled for every orb. On success:
  - RMT is unlocked (kept for good, through rerolls);
  - **real healing** of **8 HP** (`unlockHeal`), never above max health;
  - a green burst (`rmt/rmt_unlock_burst`), a heal pulse and a chime, **played locally**: only the player sees and
    hears them;
  - a private chat line, "Your body remembers how to heal." (sent to that player only).
- **Never again** after unlocking. Dying, or becoming Severed, removes a waiting orb.
- **Commands:** `/kegare debug orb spawn [player]` forces an orb now, ignoring chance and the roll cooldown, but never for
  Severed or already-unlocked players. `/kegare debug orb status [player]` shows the time to the next roll, whether an orb
  is waiting, RMT locked/unlocked, and eligibility.
- **Tests:** `GreenOrbTest`: no roll above the threshold, one roll per cooldown, then again after it; where it starts and that it
  waits; a new route every orb; following to the last tick unlocks and heals, capped at max health; staring without following never does (25 routes);
  losing it runs it back, then a second try counts; fades on time, but never under someone following it; routes stay short of walls; the payload survives
  the wire; never for Severed players (forced or rolled) or after unlocking. `OrbPathTest`: 2000 routes each stay in range, take every step, wind, and are
  random; no tick moves the orb more than a third of the look cone; the curve passes through every point. `RmtTest` also checks it has no player animation.

### 3.19 Swap (COMMON innate technique)
Package `innate_technique.swap`. Trade with other players: places, looks, effects, momentum. Malice color teal
`#14B8A6`; tab icon ender pearl. All numbers in `[swap]` of `kegare-server.toml` (seconds, blocks).

**Shared targeting** (`SwapTargeting`):
- The target under the crosshair within `targeting.range` (24) blocks, with line of sight (blocks stop it), alive and
  not a spectator. `aimTolerance` (0.3 blocks) widens the hit box a little.
- **Players or mobs:** Positions, Switchback, Send Off, Exchange and Momentum Exchange take any living mob too
  (`SwapTargeting.lookedAtLiving`), except armor stands and bosses (`c:bosses`: the wither, the ender dragon...).
  Awareness, Mimic and Total Swap take **players only** (a disguise borrows a player's look; trading health with a
  cow would be a free heal); for those, mobs neither count nor block the view.
- No valid target: fizzle with "No player in sight." (players-only abilities) or "Nothing in sight to swap with.",
  nothing paid, no cooldown.
- Stunned or frozen players can't cast (the shared checks) but CAN be swapped.

**`SwapTargetEvent`** (cancellable, `NeoForge.EVENT_BUS`, server side): fired before ANY swap with the caster, the
target (the anchor entity for a recall) and the ability. That covers every position swap (both ends of Switchback),
the recall, Send Off, both disguises, Exchange, Momentum Exchange and Total Swap.
- Cancelled: "Something stops the swap.", the cast fizzles with its Malice **spent** and **no cooldown**
  (`CastManager.fizzleKeepingCost`, INSTANT abilities only), and the caster earns *Not Allowed*.
- Swap hardcodes no immunities; a future technique cancels the event. Debug stand-in:
  `/kegare debug swap unswappable <player> <on>` (`SwapDebug`, runtime only).

**Position swaps** (`Swapper`): both move at once, player or mob (`teleportTo`, which also dismounts; sleepers wake;
a mob's pathing stops; anything that wouldn't fit where it lands is nudged up out of the blocks), and both fall
distances reset (only Momentum Exchange keeps fall distance, on purpose, and it never moves anyone).
Both ends get the move's clap (`SwapSounds`) and `swap_depart`/`swap_arrive` (see Visuals). The move reaches every
watcher at once: `moveTo` broadcasts the teleport as it happens and moves the entity tracker's base with it (server
accessor mixins `ChunkMapAccessor`, `TrackedEntityAccessor`, `ServerEntityAccessor`); otherwise the tracker's next
small step would be measured from the old spot and watchers would see the entity that far past its new one.

**Abilities** (default loadout order) and their specials (R, sharing the base ability's cooldown):

| **Positions** | INSTANT | 48 | 8 s | Swap positions AND facing with the target. |

| **Awareness** | INSTANT | 80 | 20 s | A 5 s disguise swap: everyone else sees the caster as the target and the target as the caster. |

The HUD and Sorcerer screen show Anchor's current stage cost (throw or recall).

**Disguises** (`Disguises`, VISUAL ONLY): inventories, health and data never move.
- The server keeps the map (wearer → face UUID, end tick, kind, caster) and sends all of it to every client when it
  changes and on login (`Disguises.StatePayload`: entity ID → disguised-as UUID, end tick, plus the wearer's UUID for
  the tab list).
- A disguise ends on expiry, or when the wearer or the face's owner dies, logs out or changes dimension.
- Clients draw a disguised player as their face for everyone **but themselves** (each player sees their own body, HUD
  and inventory normally):
  - name tag (`RenderNameTagEvent`);
  - skin, arm model and cape, and the tab-list head (`PlayerInfo#getSkin` mixin);
  - tab-list name (`PlayerTabOverlay#getNameForDisplay` mixin);
  - visible armor and held items, lent from the face for the length of one render (`RenderPlayerEvent`). If the
    face isn't loaded on that client, the slots are drawn empty rather than showing the wearer's own gear.
  - These are client mixins (`kegare.mixins.json`); Swap's only server ones are its tracker accessors.
- Only disguised players see the `awareness_shimmer` loop (sent to them alone, for as long as the disguise lasts), so
  they know it's on: crisp corner brackets on their own screen (see Visuals).
- **API** (either side): `Disguises.isDisguised(entity)`, `getRealIdentity(entity)`, `getDisguisedAs(entity)`; server:
  `get(player)`, `wearing(face)`. Anything that must see through disguises asks here.

**Visuals.** Every swap is a clap. The feel is a clean magic trick: a sharp clap and the swap has already happened,
smooth and modern in Swap's teal, nothing heavy, blurry or lingering, never the enderman's purple.
- PAL animations, Python-built (`tools/anims/swap.py` → `player_animations/swap.json`), each move clapping its own way:
  - `positions_clap` (Positions): the hands go straight for each other and meet low in front of the chest, then spring
    open, palms out; then dropped. The cast is instant and animations blend in over 3 ticks, so the swap lands on the
    sound and the hands meet a moment after.
  - `switchback_cast` (Switchback): a double clap, together, a hand's width apart, together again harder; then the right
    hand turns back toward the chest, the come-back. `switchback_snap` (its swap back): the right hand flicked out to the
    side at chest height and snapped down and in.
  - `awareness_cast` (Awareness): a clap, then the hands turn over and fan open, low and wide, a card shown front and
    back; held a moment, then dropped.
  - `anchor_throw` (Anchor's throw): the token flicked forward underhand, the right hand low and back, then out at the
    right side a little below level. `anchor_recall` (its swap): the right hand reaches out at the right side, as if to
    the token, and is pulled in to meet the left in a clap low before the chest.
  - `send_off_cast` (Send Off): a clap, then both palms shoved out at the target, a shoulder's width apart and level,
    the body leaning in behind them; held, then dropped. Anchor's recall reaches out at one side and pulls in, this
    pushes away with both hands at once. In your own first person the shoved hands come up at the bottom corners.
  - `mimic_cast` (Mimic): a cupped clap up by the right side of the face, the head tipped toward it; then the right
    hand drawn down past the cheek, the face taken. In your own first person the hands are always vanilla's: up by
    the face they'd only sweep across the view.
  - `exchange_cast` (Exchange): a clap, then the hands slide past each other low in front of the waist, each to the
    other's side, the trade; then they part. In your own first person they stay below the view.
  - `momentum_cast` (Momentum Exchange): a hard clap with the body thrown forward into it, then both arms flung back
    behind and the chest up, the push given away.
  - `total_swap_clap` (Total Swap): the biggest clap: the arms flung wide (out, never up) and slammed together low with
    the knees giving under it, meeting as the swap lands like every other clap; then thrown wide open, held, dropped.
  - In your own first person, a Swap animation shows its hands only while you look about level (no more than 15° down,
    `PlayerAnimations.handsWhileLevel`). They hang from the body, which doesn't tip with the view, so at chest height
    they sit at the bottom corners of a level view; looking further down they'd come up into its middle, so the hands
    are vanilla's then.
- Both ends of every swap (`SwapFx`, drawn by each client from the entity the payload names):
  - the **afterimage**: a teal figure of a player left where they stood, in the pose they were in (the clap): the
    body's boxes in flat teal, shaded by the way each face points, lit fully, with the arms this client sees on them

    first-person camera. Players only: a mob gets the ring.
  - a thin teal **ring** at the feet, widening and thinning over 5 ticks.
  - `swap_depart`/`swap_arrive` (Photon): a few tiny glints, gone in 3 to 6 ticks. Played a tick late, so the ones

    vanilla's 3 ticks, so nobody is seen crossing the gap and the arriving player's camera never sits in the other's
    head; your own head and body face the new way at once (third person).
  - Reduced: fewer glints. Vanilla: no afterimage or ring, a few small teal dust specks that are gone at once.
- Switchback's **countdown ring** (`SwapFx`, on both from the cast to the swap back): a thin teal track at the feet with a
  bright arc that drains round it over the delay, a white mark for each second still to go and a pulse as each second
  starts; gone the moment the swap back comes or it's called off. It's the `switchback_timer` loop, which runs for the
  delay (its `growTicks`; a player who comes into view later sees it at the real time left, §3.5) and is drawn by the move, not Photon. Reduced: the same.

- Mimic's **flicker** (`mimic_flicker`, the cast's effect, drawn by `MimicFlickerLayer` on the caster): their whole
  body, posed as it's drawn, flashes as a flat teal figure a pixel bigger than the skin's outer layer, on for 2 ticks,

- The disguised player's **brackets** (`SwapHud`, the `awareness_shimmer` loop: Awareness, Mimic and Total Swap):

  - Waiting: it stands on its edge just off the face it stuck to, turning slowly, and pings every 1.5 s, a thin ring

- Photon draws only `swap_depart`/`swap_arrive`'s glints (`SwapFxAuthoring` → `fx/swap/`); everything else above

  - `swap.cupped_clap` ("Cupped hands clap", hollow): Mimic's cast, at the caster only.

### 3.20 Puppet Manipulation (EPIC innate technique)
Package `innate_technique.puppet_manipulation`. Half-size puppets of yourself, charged with Malice: command them, ride
inside them, set them off, or let one stand in for you. Malice color lavender `#C4B5FD` (also the puppets' glow); tab
icon armor stand; ultimate locked (its Dominion comes later). All numbers in `[puppet_manipulation]` of
`kegare-server.toml` (seconds, blocks).

**The puppet** (`PuppetEntity`, a `PathfinderMob`; saved with its chunk, never despawns, no loot or XP):
- A copy of its owner at **half size** (the 1.21 `scale` attribute, `puppet.scale` 0.5; its hitbox too). It is drawn
  with the owner's real skin and arm model (`PuppetSkins`: from the tab list while the owner is online, else from the
  skin property the puppet carries, so offline owners' puppets still look like them; never a Swap disguise).
- **Charge tier** (`PuppetTier`) set by Puppet Creation's charge:

  | Tier | Charge | Cost | Health | Glow |
  |---|---|---|---|---|
  | Tap | released before `halfCharge` (0.6 s) | 40 | 2 | faint |
  | Half | before `fullCharge` (1.5 s) | 100 | 4 | normal |
  | Full | full charge | 180 | 8 | bright, plus an outline in the glow color |

  The glow is a shell of drifting threads just outside the body (`PuppetGlowLayer`, additive, texture
  `entity/puppet_glow.png`: hard one-pixel threads woven four each way, no soft edge, tiling seamlessly) in the owner's
  Malice color. The Full outline uses vanilla's outline pass, but only while the viewer has line of sight, so it never
  gives a hidden puppet away through walls; a new Full puppet's outline comes as its weave finishes (`puppet_form`).
- Barely any melee (`meleeDamage` 1, reach 1.4 blocks from its centre so a small body can still land it), and
  `movementSpeed` 0.42: a little faster than a walking player; a following puppet more than 6 blocks behind runs at
  1.35× and keeps pace with a sprint, and one more than `followTeleportDistance` (24) behind appears beside its owner.
- **Kuru kuru:** standing still for `spinDelay` (0.5 s) it spins (`puppet_idle_spin`, arms out). Decided on the server
  and synced, so every viewer agrees. Never while possessed or standing in.
- **The cap:** `maxPuppets` (15) per player, counting puppets in unloaded chunks too (`PuppetSavedData`). At the cap,
  Puppet Creation fizzles for free ("You can't hold more than 15 puppets."). A puppet that dies, dissolves or detonates
  frees its slot at once. Lowering the config never removes puppets: a player over the new cap keeps theirs but can't
  make more until below it.
- Lasts until killed: it survives its owner's death and logout. While the owner is offline (or dead, or in another
  dimension) it stands idle and never attacks.
- **Rerolling away** (reroll, rebirth, admin) dissolves EVERY puppet the player owns into Malice-colored threads
  (`puppet_dissolve`). `PuppetSavedData` (`data/kegare_puppets.dat`) keeps each owner's puppet UUIDs (the cap) and a
  **generation**: rerolling away bumps it, so a puppet in an unloaded chunk finds it is stale on its first tick after
  loading and dissolves then. Even if the player rolls Puppet Manipulation again later, old puppets never come back.
- **API** (`Puppet`, for future systems): `hasSoul()` (always false), `ownerId()`, `maliceColor()`, `tier()`.

**Possession** (`Possession`, `PossessionData` saved on the player as `kegare:possession`):
- **The hidden puppet touches nothing.** It isn't pickable or pushable and doesn't push (`PuppetEntity.pushEntities`). Its tick stops only on the server, and
  vanilla has mobs shove overlapping players on the client, so without that a puppet trailing a step behind pushes its possessor along endlessly.
- The player **becomes the puppet**: they take its place, its size (a `scale` modifier) and its health (a max-health
  modifier; it doesn't heal). Their inventory is stashed in the record (no items; nothing can be picked up and no
  container opened). Weak melee only (empty hands). **No casting:** a `CastManager` interceptor
  (`CastManager.addInterceptor`, first say over every key intent) lets R return and answers every other cast with "You
  can't cast while possessing. Press R to return."
- The body stays behind as a **shell** (`PuppetShellEntity`, never saved): their skin, armor and name, standing slack
  with its head bowed, motionless (no knockback, not pushable) and defenceless. The puppet waits hidden inside the
  player and can't be hit; others see the player drawn with the puppet's glow and no name tag, and a thin lavender
  thread from the shell to them (`possess_link`, drawn by each client: a pale core in a lavender strand with a slight
  sag, shooting out from the shell over 5 ticks as it starts, kept while they possess, never drawn into your own eyes).
- **Ways back** (each puts back real health, size, inventory, and the position at the shell; items picked up meanwhile
  are kept, never lost; the puppet comes back out where they left it, with what health they left it):
  - R again;
  - **the shell takes any damage:** snap back at once, and the hit lands on the real body;
  - **the puppet dies** (lethal damage while possessing kills the puppet, not the player): snap back with
    **backlash**: Nausea (4 s), a stun through the shared stun system (1 s), and 80 Malice lost;
  - more than `maxDistance` (64) from the shell;
  - logout (before the player is saved), death (a real death, e.g. `/kill`, returns them first and goes ahead in the
    body), a dimension change (before travelling) or losing the technique.
  - A server stop mid-possession: the saved record puts everything back on the next login.
- **HUD** (`PuppetHud` payload, sent only when it changes): "Possessing" and the body's health under the crosshair, in
  and out of Technique Mode (`StatusLayer.addExtra`).

**Strings** (`Strings`, runtime only: nothing is saved; `[puppet_manipulation.strings]`):
- **Stage 1 (its number key):** fire a string at the player, mob or puppet you're looking at, within `range` (24), line of sight
  required (`PuppetTargeting.lookedAtStringTarget`: not armor stands, empty bodies or possessed puppets). Another player's
  puppet counts as a mob. Nothing in sight: free. One string at a time. It waits up to `life` (8 s), and snaps if stretched
  beyond `snapRange` (32). Firing has only a `fireCooldown` (0.25 s) lockout, so a double press can't fire and pull at once.
- **Stage 2** depends on the key and what you're looking at:

  | Key | Same target, or nothing | A different valid target (within `range`) |
  |---|---|---|
  | Cast | **Reel In** (48): pull the target to you, stopping `arriveDistance` (2) short | **Tie** (80): both are pulled into each other at `pullSpeed` (1.2 blocks/tick); at `collideDistance` (1.2) both stop and take `tieDamage` (1.5, `kegare:strings_tie`, credited to you, no knockback; a weak puppet's 2 health survives it). Then they stay within `tetherDistance` (3) of each other for `tetherDuration` (4 s) |
  | R | **Zip** (40): pull yourself to the target | **Leash** (100): both stay within `leashDistance` (6) of you for `leashDuration` (5 s), and you lose `leashSlow` (35%) of your speed while they do. They can still attack and cast |

- **Holding:** past a tether or leash's limit, a target is dragged back at `dragSpeed` (0.4 blocks/tick, faster the further past, up to `pullSpeed`), so it can't be outrun. A Tie's string runs between its two targets, so you can walk away from it, and it drags both ways. A pull gives up after `pullTimeout` (2 s; a wall in the way). A Tie that times out skips the collision but still tethers.
- **Pulls** are velocity, not teleports: every tick on the server, sent to a player's client (`hurtMarked`), which is what actually moves them. A client lags a tick or two, so pulls ease off over their last stretch rather than overshoot.
- **Cooldown:** starts at stage 2 (running effects finish on it), or when a string that never got a stage 2 snaps, expires or loses its target.
- **R with no string:** free, "No string attached."
- **`StringsTargetEvent`** (cancellable, `NeoForge.EVENT_BUS`, server side): fired at stage 2, once per target, with the caster, target and `StringsVariation`. Cancelled: that target isn't moved (a cancelled Zip doesn't move the caster: the target refuses). If nothing is left to move, the cast fizzles like a refused swap: Malice spent, no cooldown, "The string won't pull.", and the string is gone. Strings never cancels it itself; `/kegare debug strings unmovable` is the debug stand-in.
- **Bosses** (`c:bosses`): strings attach, but they're never moved. Reel In, or a Tie or Leash of two bosses, fizzles for free ("It won't budge.") and the string stays for a Zip. Zip works: you move. A Tie of a boss and something else pulls only the something else, and the boss takes the collision damage. A Leash holds only the something else.
- **Ends** with the death, logout or dimension change of the caster or anyone on it, and when you possess a puppet (or the puppet on it is possessed) or lose the technique. A puppet on a running pull, tether or leash stops following its owner, so it doesn't teleport off the string.

**The string on screen** (`StringsClient`, `StringsSync` to everyone in the dimension: the string is the tell). It's emissive, and the segment is laid at its true length along a shallow curve: a longer string has more segments, never stretched ones, so the braid can't smear, and each overlaps the next slightly so a bend can't open a gap. ### 3.21 Progression (package `progression`)
What a player builds up over time: **Grade**, **Assessment**, **Refinement** and **Insight**, plus a registry for what they
unlock. **None of it changes damage, costs, cooldowns or Malice capacity.** Every number is in `[progression]` of
`kegare-server.toml`. The server decides everything; the client only displays synced values.

| | Belongs to | On reroll | On death | Seen by |
|---|---|---|---|---|
| Grade | the player | kept | kept | its owner only |
| Assessment | the player | kept | kept | its owner only |
| Refinement | the current technique | **reset to 0** | kept | its owner only |
| Peak Refinement | the player | kept | kept | its owner only |
| Insight | the player | kept | kept | its owner only |
| Technique-tied framework unlocks | the current technique | **lost** | kept | its owner only |
| Grade and Insight framework unlocks | the player | kept | kept | its owner only |

`/kegare rebirth` clears the technique, so it counts as a reroll here: Refinement resets, and everything else stays.
`/kegare progression reset` is the full wipe.

#### Fight tracking (`FightTracker`, `Attribution`)
The one record of who damaged whom, how much and when. Grade, Assessment and Insight all read from it.
- A fight is between two players. It ends after `fights.timeout` (30 s) with no damage between them, or on a death or a logout.
- **Win:** the opponent dies during the fight and you dealt at least `fights.winShare` (25%) of the damage they took from
  players in it. If they die and you fall short of that, it counts as surviving. **Wins only affect XP, never Assessment.**
- **Never counted:** damage to yourself, your own puppets or shell, and environmental damage with no attacker.
- `Attribution` decides who is really behind a hit: a puppet's punch is its owner's, a projectile's is its caster's.
- A landing that deals no damage (a swap, a string) opens a fight too. A hit's counted damage is capped at the victim's max
  health. Windows and timers use overworld game time.

#### Grade
Ladder: Grade 4 → Grade 3 → Semi-Grade 2 → Grade 2 → Semi-Grade 1 → Grade 1 → Special Grade. Everyone starts at Grade 4.
**Grade never goes down** (only an admin command can lower it) and **never changes Malice capacity.**

| Step into | XP (`grade.xp_to`) | Assessment |
|---|---|---|
| Grade 3 | 200 | no |
| Semi-Grade 2 | 500 | no |
| Grade 2 | 1000 | **yes** |
| Semi-Grade 1 | 2000 | no |
| Grade 1 | 4000 | **yes** |
| Special Grade | none | **yes: Assessment only, never XP alone** |

**There are no trials anywhere on the ladder. No promotion requires killing or beating anyone, at any rank, player or
boss.** Promotion depends on how well the player uses their technique.

- **Earning XP** (mostly PvP): `xpPerDamage` 2 per point dealt to a player, `xpWin` 40, `xpLoss` 15 (losing still teaches),
  `xpSurvive` 20 for a fight nobody died in (you must both deal and take `surviveMinDamage`, 1: a tap isn't a fight). If you log
  out you keep only the damage XP. A fight with no damage gives nothing. Severed players earn Grade normally.
- **Mobs** give `xpPerMobDamage` 0.1 per point, up to `mobXpPerWindow` 40 per window, so solo players progress slowly and a
  farm can't replace fighting.
- **Diminishing returns:** each earlier fight against the same player in the rolling hour (`rollingWindow`) multiplies a fight's XP
  by `fightDecay` 0.6, down to `fightDecayFloor` 0.05.
- **Far weaker opponents:** a fight's whole XP loses `weakerPerGrade` 35% per Grade the opponent is below you, down to `weakerFloor` 2%.
- **Stronger opponents:** the win XP (only) gains `winBonusPerGrade` 50% per Grade they are above you, up to `winBonusMax` ×3.
- XP past a step carries over, capped at the next step's cost. There is no XP at Grade 1 or above.
- **Visibility:** only the player sees their own Grade. It's synced to its owner only, and promotions are private with no chat line.
- **API:** `Progression.getGrade(player)`, server side, for later systems.

#### Assessment (how well you use your technique)
Each **qualifying** PvP fight gets a 0-100 score: it lasted `qualifyMinLength` (10 s, first event to last hit) and both players dealt
`qualifyMinDamage` (4). **Kills and wins add nothing,** so a player can reach Special Grade without ever winning a fight:
`AssessmentScoring` isn't even handed who won or died. **Capacity, rarity and traits are never inputs,** so a Low Malice player can
reach Special Grade. Assessment is private and never lowers Grade.

| Part | Weight | What it rates |
|---|---|---|
| Technique use | 50 | Below, against the kit at their **Peak Refinement** level, or what they have unlocked if that's more |
| Efficiency | 25 | Damage dealt per **base** Malice cost of what you cast (full marks at `efficiencyFull`, 0.08) |
| Performance | 15 | Your share of the damage traded (full marks at `performanceFullShare`, 70%) |
| Opponent | 10 | `opponentEven` 0.8 for your own Grade, +0.1 per Grade above, −0.3 per Grade below, down to 0.02. **A stronger opponent is never required:** an even fight can score 98 |

- **Technique use** splits into distinct abilities landed (40), distinct specials landed (25), landing both a base and a special (10) and
  combining (25: different abilities landed back to back within `comboWindow`, 4 s, three for full marks). Landing 60%
  (`distinctFullShare`, rounded up) of the kit earns full marks on variety. With no special in the kit yet the special parts drop
  out and their weight goes to the rest.
- **Rerolling can't flatter it.** Peak Refinement survives a reroll, so the kit is the current technique's at that level (`TechniqueUnlocks.scoringKit`),
  or what's unlocked if that's more. Below their peak, combining also asks for three different moves, not just three combos. Grade 1 takes Peak 5, and from
  there alternating any two moves below their peak scores at most 52.5, under its 60. Someone at their peak isn't affected: a fresh player
  alternating their two level 0 moves still scores 100, and a player really at level 5 or 6 alternating one ability and one special still scores 60.8. The three-moves rule is for players below their Peak only. A rerolled Peak 10 player can reach Grade 1's
  minimum from level 1 with three moves (70), and Special Grade's from level 3 (91.7).
- **Repeating one move scores low:** past `spamFreeShare` (50% of your landings) one move lowers Technique use, down to 40% of it
  (`spamPenalty`) when it's every landing. The other three parts don't look at variety, so a perfect one-move fight can still reach
  about 49. That's under Grade 2's 50, but only just, so keep it in mind when changing the weights.
- **Efficiency uses base cost,** so capacity and Six Eyes discounts never inflate it. `Landings.baseCost` divides out what the
  surroundings changed. **Any future discount must be divided out there too.** It counts all damage dealt, melee included (Swap's abilities
  deal almost none), plus upkeep as spend and casts in the `openingCastSeconds` (5 s) before a fight. Nothing cast scores 0. Shared
  abilities (RMT) are left out.
- **Severed players** have no technique or Malice: melee variety takes Technique use's weight (distinct moves, by weapon and by crit,
  sprint or ranged, plus the melee layer's three against real players: `perfect_parry`, only off a swing with a full attack bar (`melee.parry.assessmentCharge`), `clean_dodge` and `reinforced_strike`; `severedFullMoves` 4 for full marks, plus combining, all with the same repeat decay), Efficiency drops out and the rest is rescaled to 100. They can
  reach Special Grade. A parry or dodge often comes before any damage: like opening Malice it waits `openingCastSeconds` for the fight, and never opens one, so what a fight is and which ones qualify don't change. A Strike is recorded as itself and not also as the weapon's hit: one hit, one move.

**Your Assessment is the average of your recent qualifying fights,** which needs a minimum number of different opponents so one friend
can't carry it:

| Grade | Average | Technique use | Over the last | Different opponents | Peak Refinement |
|---|---|---|---|---|---|
| Grade 2 | 50+ | 40+ | 5 fights | 2+ | 2 |
| Grade 1 | 70+ | 60+ | 10 fights | 3+ | 5 |
| Special Grade | 90+ | 85+ | 20 fights | 3+ | 10 (the top level) |

**Spam can't qualify.** Efficiency, performance and the opponent bonus can carry a one-move fight past 50, so every gate also asks for an average
Technique use over the same fights (`minTechniqueUse`, 0-100; each fight's is stored with its score). One move repeated scores 12 at most, a real
mix about 40, varied play 80 or more. Special Grade's has to be above 80 to mean anything, since with every other part full a 90 average already
takes that. A Severed player's melee variety stands in, and is reachable at every gate. The score's weights are unaffected. Fights saved before this
count as Technique use 0 and roll off as new ones come in.

**Peak Refinement** is the highest level ever reached on any technique. It survives rerolls, so rerolling doesn't block promotion. Severed
players skip it. Promotion is tried after every qualifying fight, XP change and new Refinement level, and on login.

#### Refinement (per technique, resets on reroll)
Levels 0-10 (`refinement.maxLevel`). It **only unlocks things**: it never changes damage, cost or cooldown. Severed players have none.

- **Curve:** level L costs `xpBase × L^xpExponent` (30 × L^1.6): 30, 91, 174, 276, 394, 527, 675, 836, 1009, 1194. Level 2, the third ability, takes
  121 XP in total, and level 9, the full kit, takes 4012.
- **Per landing:** `baseXp` 1 for a base ability or ultimate, `specialXp` 2.5 for a special; ×`playerMultiplier` 3 on players (mobs still
  count, so a player can practice alone); ×`targetDecay` 0.97 per earlier landing on that target in the rolling window, down to 0.2;
  × the Grade multiplier.
- **Grade multiplier** (`grade_multiplier`): Grade 4 ×1, Grade 3 ×1.1, Semi-Grade 2 ×1.25, Grade 2 ×1.5, Semi-Grade 1 ×1.75, Grade 1 ×2,
  Special Grade ×2.5. An experienced sorcerer re-learns faster after a reroll.
- **Earned only by landing the CURRENT technique's abilities on real targets.** Casting into the air gives nothing, and neither do your
  own puppets and shell. Armor stands aren't real targets.
- **An idle owner earns nothing from their puppets.** A puppet's own hit (`OwnedEntity.actsOnItsOwn`) earns Refinement, and Grade XP on a mob, only within
  `ownerActiveWindow` (30 s) of the owner personally landing a hit or an ability on a real target (`Landings.isActive`). A Curio Burst is their own doing and counts;
  being hit doesn't, and neither does an ability with no target, since it wasn't landed on anyone. The puppet keeps fighting either way, and on a player its hits stay on
  that fight's record.
- **Rerolling resets it to 0;** Peak Refinement stays.

**The shared path (`Landings`): a new technique needs no Refinement code unless an ability has no target.** `CastManager` runs every execute,
tick and end in a `CastScope`, and entities spawned there carry a `CastOrigin`.

| How it lands | Abilities |
|---|---|
| Automatic: damage traced to a cast, or to an entity one spawned | Frost Shard, Glacial Lance, Splinter, Glacial Spire, Curio Burst; Puppet Creation through its puppets' hits |
| Automatic: an effect or knockback put on someone else during a cast | Frost Field, Shatter Shell |
| A shared check or the ability calls `Landings.land` (it lands without hurting) | Positions, Switchback, Awareness, Mimic, Send Off, Exchange, Momentum Exchange, Total Swap (all through `SwapTargeting`); Strings, Zip and Leash; Focus |
| `Landings.during` runs a delayed effect under its cast | Chain Burst's later bursts, Tie's collisions |
| The technique says whose hit it was (`Attribution.addAttributor`) | Possess: melee while inside a puppet |
| `Ability.hasNoTarget()`: counts only within `landing.noTargetWindow` (10 s) of trading a hit with something real | Ice Path, Anchor, Directive, Understudy, Stand-In |

Two don't fit that pattern. **Rime Shell** is a toggled self-buff, so it lands on whatever it blocks (`RimeEvents`). **Reverse Malice Technique** is
shared and targets its caster, so it never lands: no Refinement, not in Technique use, and its Malice is left out of Efficiency.

The same ability landing on the same target counts once per `landing.repeat` (1 s), so one volley or channel isn't twenty landings.

#### Extension technique unlocks
Abilities, specials and the ultimate of an innate technique unlock through Refinement. Each technique defines the level in its definition
(`UnlockTable`, `Builder.defaultUnlockLevels()`, `Builder.unlockLevel`), and `refinement.unlockLevelOverrides` overrides any of them from the
config (`["kegare:frost_field=1"]`). **Datagen fails if a non-test technique sets none.**

| Level | Default | Rime | Swap | Puppet Manipulation |
|---|---|---|---|---|
| 0 | abilities 1 and 2 | Frost Shard, Glacial Lance | Positions, Awareness | Puppet Creation, Directive |
| 1 | special of 1 | Splinter | Switchback | Possess |
| 2 | ability 3 | Frost Field | Anchor | Curio Burst |
| 3 | special of 2 | Glacial Spire | Mimic | Focus |
| 4 | ability 4 | Rime Shell | Exchange | Understudy |
| 5 | special of 3 | Ice Path | Send Off | Chain Burst |
| 6 | ability 5 | | | Strings (with Reel In and Tie) |
| 7 | special of 4 | Shatter Shell | Momentum Exchange | Stand-In |
| 8 | ultimate | locked until Dominions | Total Swap | locked until Dominions |
| 9 | special of 5 | | | Zip and Leash |

Test techniques have everything unlocked. A level past `maxLevel` means `maxLevel`; abilities past the fifth wait for level 10 unless set; an
ultimate's special comes with the ultimate.

- Casting a locked ability or special **fizzles at no cost and no cooldown**, with "Requires Refinement X."
- Locked abilities can't be placed in the loadout. **Shared abilities like RMT are not gated by Refinement** and keep their own unlock rules.
- A new unlock brings a small private toast and goes into the first empty loadout slot, if there is one.
- On reroll the loadout resets to the new technique's level 0 kit. Shared abilities stay unlocked.
- Lowering Refinement through an admin command takes newly locked abilities off the loadout.
- `requireRefinementForAbilities` (default true): false unlocks everything, for testing and casual servers. Flipping it live re-validates
  everyone online. Refinement is still earned.
- Players from before progression log in at Refinement 0 and drop to the level 0 kit.

#### Insight (player, kept on reroll and death)
Three separate categories: **DOMINION, WARD, OUTPUT**. `Insight.recordFirst(player, firstKey, category, amount)` pays each `firstKey` once per
player, ever, saved per player. Which category each source pays into, and how much, is in `progression.insight`.

| Source (`InsightHooks`) | Default | Pays once per | Status |
|---|---|---|---|
| `hit_by_technique` | Ward 1 | technique (any landing on you, damaging or not) | wired |
| `first_legendary_fight` | Output 5 | ever | wired |
| `survived_standstill` | Ward 5 | ever | wired |
| `hit_by_maximum_output` | Output 5 | technique | hook only |
| `caught_in_dominion` | Dominion 5 | technique | hook only |
| `clashed_with_dominion` | Dominion 5 | technique | hook only |
| `book_chapter` | Dominion 2 | chapter of a later system | hook only |

The hook-only ones wait for systems that don't exist yet: those systems call the `InsightHooks` method. **Insight does not change extension
technique unlock levels.** It lowers only framework requirements (below).

#### Unlock framework (`Unlocks`)
For shared and system unlocks, separate from a technique's own abilities.
- `Unlocks.register(id, requirements)`, with `UnlockRequirements.builder()`: `.grade(minimum)`, `.refinement(minimum)`,
  `.insight(category, minimum)`, `.loweredBy(category)`, `.tiedToTechnique()`. Check with `Unlocks.has(player, id)`; hear of changes with
  `Unlocks.addListener`.
- **Insight lowers the Refinement needed, but can't remove it,** for an entry that names a `loweredBy` category: `refinementLoweredPerInsight` (0.1)
  levels per point, rounded down, so 10 Insight is 1 level. It takes off at most `refinementLoweredCap` (0.5) of the requirement, also rounded down:
  10 needs at least 5, 5 needs 3, 2 needs 1, and 1 stays 1. A requirement of 1 or more never reaches 0 whatever the cap is set to.
- **Re-evaluated whenever Grade, Refinement or Insight changes,** and on login.
- **The flag is on each entry.** `tiedToTechnique` entries are per technique and are lost on reroll. Others stay once earned, even if an admin
  later lowers the Grade.
- **A Severed player can't reach a Refinement-gated entry.** They have no Refinement and Insight can't make up for all of it. Anything they should
  be able to earn is registered by Grade and Insight alone.
- **Nothing real is registered yet.** Dominions and later unlocks plug in when built. Tests use a
  test-only entry.
- **Severed players and the planned unlocks.** Planned defences against sure-hits can use Refinement requirements: Severed players don't need them, since
  sure-hits can't target them. Dominions and some other planned unlocks are also not for Severed players.

#### What the player sees
- **Sorcerer screen:** the Progress view, and greyed locked tiles and cards (§3.12).
- **HUD:** empty slots stay empty, a locked special's R plate is dull, and the ultimate slot shows a padlock until it's unlocked (§3.6). No Grade or XP
  on the combat HUD.
- **Toasts** (`ProgressionToast`, sent to the earner only): one on promotion and one on each unlock, held during the roll reveal like other toasts.
  A promotion that earns an advancement also shows that advancement's own toast, to the same player. Levels with nothing to unlock show none.
- **Saved** with attachments (§2), copied on death. Synced to the owner only, in `SyncPayload`, never with an attachment's own `.sync`.
- **Advancements** (§3.11): silent and hidden. Every existing technique advancement can still be earned, because each is awarded by using an ability
  that a level from 0 to 9 unlocks; none needs a Dominion. Swap's Total Swap ones wait for level 8.

#### Rules for every future technique
- **It gets Refinement through the shared path.** It writes no Refinement code of its own, unless an ability has no target (`hasNoTarget`) or lands
  without hurting (`Landings.land`).
- **It sets unlock levels for its abilities, specials and ultimate.**
- **It registers any other unlocks through the framework** (`Unlocks.register`), never with its own check.

**Tests:** pure maths in `FightTest`, `GradeMathTest`, `AssessmentScoringTest`; in-game JUnit in `FightTrackerTest`, `GradeTest`, `AssessmentTest`,
`LandingsTest`, `RefinementTest`, `TechniqueUnlocksTest`, `InsightTest`, `UnlocksTest`, `ProgressionSnapshotTest`, `ProgressionAdvancementsTest`.

### 3.22 The melee layer (package `melee`)

Dash, Parry and Reinforced Strike, for every player, in and out of Technique Mode. They aren't techniques: no slots, no casting, no Refinement or Assessment
gates, and counters to techniques have nothing to act on. Low Malice is what limits them, and RMT doesn't touch them.
Dash is Kinetic Manipulation; Parry and Strike are Reinforcement, which "can distribute stress and absorb energy; it cannot delete the reaction": hence the guard's
recovery. Numbers: `[melee]` in `kegare-server.toml` (`MeleeConfig`), resolved per player by `MeleeNumbers`. State: the runtime attachment `kegare:melee`
(`MeleeState`, in level game time, gone on death and logout, like a cast in progress).

**Who can use it** (`MeleeRules`): alive, born, not a spectator, not stunned or frozen, and not possessing a puppet (the body isn't yours to reinforce; a Strike
ready when you possess is dropped).

**Dash** (double-tap sprint, or a rebindable key with nothing bound by default).
- About 4 blocks the way you're moving, or forward with no keys held; 3 s cooldown; 25 Malice. No invulnerability.
- The double tap (`DoubleTap`) follows the sprint key if it's rebound, in a window set by client config `input.dashDoubleTapMillis` (300; 0 = off), also on the Settings page.
- The client only says which movement keys are held (clamped on arrival). The server checks everything and sweeps the player's box through the world (`Dash.clearDistance`; a
  step counts as passable), so it never aims past a wall. Less than 0.5 blocks of room refuses it for free, with no cooldown. It's not allowed on a mount or while gliding.
- **Who moves the player:** the server allows the dash and tells the owner once (`MeleeDashPayload`), and `client/DashDrive` sets velocity each tick, measuring how far it's actually got.
  The game's own collision stops it, so it can't clip. Velocity pushed from the server each tick would land anywhere from 3 to 5 blocks, because two pushes in one client tick lose
  one. A dash covers 4.33 blocks in the open and stops flush against a wall. A stun stops it (`MeleeDashPayload.STOP`). It adds nothing to fall handling: dashing doesn't save you from a fall.

**Clean dodge** (`CleanDodge`). A dash leaves a "ghost": the box the player had when they left. For 0.5 s, the first thing that would have hit the ghost and wouldn't hit the player now counts, and earns a Strike:
- a **melee swing**, polled each tick: anyone just starting a swing whose reach gets the ghost (a player's look ray to their reach, stopped by blocks; a mob's reach box);
- a **projectile**, polled each tick: its next two ticks of flight cross the ghost (stopped by blocks), and don't cross the player;
- an **ability area**: area abilities call `CleanDodge.areaWentOff(level, owner, covers)` with the same test they use on targets (Curio Burst, Glacial Spire, Shatter Shell, Frost Field).

A real hit from any entity in the window ends it; your own swings, shots, areas and puppets don't count. A new area ability adds the one call. Mobs seldom qualify on melee: their AI only swings at a target already in reach.

**Parry** (hold X, rebindable). All timed on the server from when the press arrived.
- **First 0.3 s, the perfect window (free):** a melee hit is cancelled, the attacker staggered (0.5 s of Slowness III, a player's attack cooldown restarted, nothing done to their abilities; a mob's own attack cooldown has
  just started anyway), and a Strike earned. Techniques and projectiles are never parried.
- **After that, the guard:** 40% off melee, draining 16 Malice/s; it drops when the Malice runs out. Holding needs 10 Malice to begin (not spent).
- **The whole time:** 10% off technique damage. Plain arrows get nothing.
- **Letting go:** 1 s recovery with no parry. Casting, attacking, dashing, a stun or running out of Malice also bring it down. A guard that caught nothing plays the exposed recovery animation.
- Stunned players can't parry. A guard can't start during a charge or a channel.
- **Bosses (§4):** can't be staggered, so their hits in the window aren't cancelled: the guard takes its 40%, no Strike. It isn't directional and doesn't slow you: both are tuning options.
- A modified client can't get a second window without sitting out the recovery; one that never lets go only drains itself (a Severed guard has a time limit).

**Melee, as far as this layer cares** (`MeleeHits`): the player, mob and no-aggro attack damage types, dealt directly by the attacker, outside a cast. Technique: any `kegare` damage type, or anything `Attribution` puts on an ability.

**Reinforced Strike** (no key, no slot). After a perfect parry or clean dodge, the next melee hit on a real target within 1.5 s does 50% more with extra knockback and costs 20 Malice by itself.
Without the Malice the hit stays normal and the Strike waits until it expires. Earning it again restarts the clock; it never stacks. Bosses take the damage and aren't moved. **Reinforced** shows on the owner's HUD, and the attacking hand shows it to everyone (below).

**The ready fist** (`MeleeTell`, `client/FistTell`). While a Strike is ready, Malice burns round the attacking hand, seen by everyone and in first person: chunky pixel-art fire wrapped round the hand and lower forearm, flickering frame by frame, little curls coming off it, and a burst in the same color when the Strike lands. A player's Malice color is their Innate Technique's (`InnateTechnique.maliceColor`), so a new one gets it by itself; `MeleeTell.bright` draws the same hue at full brightness because Innate colors can run dark and a dark fire isn't one.
- *Fire:* `client/FistFire`, from the greyscale sheet `textures/entity/fist_fire.png` (`tools/gen_art.py`). It's built as two slightly inflated copies of the arm that follow it in every pose, wide and slim, with cutout pixel fire unwrapped round them, so it wraps the arm from every side. The inner tube sits tight on the arm (0.4 of a pixel out, clear of the skin's sleeve), with a paler heart on it. The outer one is 1.6 pixels out, and its tips, tallest on the arm's corners, break past the arm's outline and give it a silhouette at 7 blocks. A tube has more texels than the arm, not bigger ones, so one texel stays about one pixel of skin. Eight looping frames at ten a second, with each layer on a different frame. It's strongest round the fist, with gaps that let the hand show, thins up the forearm and breaks into small dark scraps near the elbow. Tongues rise from narrow bases and sway. On an arm held up they go the other way, past the knuckles (a second row of frames in the sheet). A side seen nearly edge on squashes into a thin line that reads as wire, so it isn't drawn; the end of the fist shows only when the arm points at you, and it's enough there, so there's no camera-facing flare. Curls start on the fire's surface partway up it, stay in a small spiral and last half a second, so they look like they came off it. It's drawn from the player's render layer, in the arm's own space.
- *Reading it:* hard edges and depth writes, no additive light, which washes out against a bright sky, and no soft alpha: every texel is solid or a hole, because soft alpha reads as glass. About a third of the fire is near-black, along the shaded side of each tongue and in flecks, grey dark enough to stay near-black after tinting. That's what holds the shape against a sky of nearly its own color (Puppet and Rime). Tips stay lit, and the bottom row of the fire never runs dark, because a run of near-black there reads as a bar under the fist. The heart goes only about a third of the way to white, because any paler and Rime looks like ice. It ignores the world's light, so it burns the same at night.
- *First person:* the hand is too close to the camera for the arm layers, which stretch into big slabs filling the corner. So your own empty hand has flat fire from `textures/entity/fist_flame.png` (`client/FistFlames`): quads on the arm's axis turned to face the camera, the mass behind and licks and a heart in front, at half the width and 0.6 of the height. With something held vanilla draws no arm, so `FistFire.drawGrip` burns one upright clump round the grip, facing the camera: a layer behind what's held and a layer in front, with gaps so the item shows through, all of it on screen in the lower right. Its own frames in `fist_fire.png`, with a rounded bottom. Vanilla's hand pass comes out relative to the camera along the world's axes, so anything that faces the camera there has to use the camera's own axes. Curls come off the clump, small and in close.
- *Tint:* both sheets are tinted at runtime. Strike effects are authored white too; `PhotonEffects.tint` sets the start color of every emitter named `tint*` on that instance. The fire shows at all three effect settings; the curls come at full and half rate on full and Reduced, and Vanilla has dust instead (none in first person). An invisible player shows nothing.
- *Disguises:* the server sends everyone but the wearer the look of the face they're wearing (`seenByOthers`), and the wearer their own. Nothing in the packet carries the real color. A Severed face shows the physical tell; a face that has gone gets the neutral default color, never the real one. `seenByOthers` is the one place a future deception would hook in.
- *Severed* have no Malice to show, so theirs is physical and doesn't glow: a strained, darkened forearm (`fist_strain.png`, lit like the skin), steam off the fist (`melee/fist_steam`) readable at 7 blocks day and night, and dust and grit on a landed Strike (`melee/strike_impact_physical`).
- *Colors of the impacts:* the Strike impact takes the Innate color: it's what was on the fist going off, and gold under an Innate burst reads as two separate effects. The parry stays gold: it's the same cue whoever parried, and pale blue and lavender go thin against the sky.
- *Information:* the color says which Innate you have before you've cast anything. §1 keeps techniques out of secret identity, so that's allowed, but it's a deliberate exception to silent PvP information, and it's only ever shown after a parry or dodge.

**Severed** trade all their Malice for superhuman abilities, so their melee is stronger than standard, with no costs. `[melee.severed]` has their own numbers: dash 6 blocks every 2.5 s; perfect window 0.3 s; guard 50% off melee and nothing off techniques, held at most 4 s (no Malice to run out of); recovery 0.75 s; Strike +75% with more knockback than standard (0.9 against 0.6). A config file from before these numbers moves to them unless a value was changed by hand (`KegareConfigMigration`, version 3).

**Impact moments** (`MeleeImpact`): `DASH_BURST`, `CLEAN_DODGE`, `PARRY_PERFECT`, `GUARD_HIT`, `STAGGER`, `STRIKE_HIT`, fired on the server tick the effect is applied. Sounds and effects hang off them, and `MeleeImpact.listen` is where the Impact System (§3.23) hooks in: each moment's listener gets both fighters where it has two (a parry's attacker, a Strike's striker).

**Visuals.** Animations: `tools/anims/melee.py` → `player_animations/melee.json` (four dash directions, `parry_guard`, `parry_perfect`, `parry_recovery`, `stagger`, `reinforced_strike`). A reaction's key pose is on its first frames, because the server has already applied the hit when it starts. Raised arms fill the first-person view, so parry and stagger throw arms out and not up. On the player's own first-person screen every melee animation leaves the hands to vanilla (`PlayerAnimations.keepVanillaHands`): PAL's first-person model draws what's held at its real size right by the camera, usually edge on, so a sword or an axe would fill the view with its dark outline and hide the opponent. `GuardHand` draws the guard instead: vanilla's hand and item brought in and turned across the body, with a short shove on a perfect parry. Everyone else sees the full animations.
Effects (`MeleeFxAuthoring`, `fx/melee/`): dash burst on the ground left behind, afterimages and a wake along the dash, parry spark and guard hit riding the defender's look (a point at the contact is too near both fighters' cameras to draw), with quieter versions on the player's own first-person screen, and Strike impact on the target (`strike_impact`, `strike_burst`, tinted). The parry's crescent is a Blockbench model, `art/blockbench/parry_arc.bbmodel` (`tools/blockbench/build_parry_arc.py`) exported to `models/fx/parry_arc.obj` and drawn by Photon's Model render mode. The model holds its shape from every side and takes the gold cleanly, where Photon's stock SLASH sprite turns to every camera, keeps a blue edge and whites out the first-person view.

**A dash from inside it** (`client/DashFeel`, its numbers in `DashKick`), where the trail everyone else sees can't be drawn. First person only: a field-of-view kick (16% at its peak two ticks in, gone by eleven; the hand's own view stays put) and needle streaks round the screen's edge, flowing from where you're headed: outward going forward, inward going backward, off to the side going sideways. Nothing is drawn inside the middle 60% of the screen. Reduced is half the kick and fewer, fainter streaks; Vanilla is neither, and vanilla's own FOV Effects slider scales the kick too. Its light shake is the Impact System's (`DASH_BURST`, §3.23).

**Tests:** `MeleeLayerTest`, `MeleeTellTest` (in-game JUnit), `DoubleTapTest`, `DashMotionTest`, `DashKickTest`, `MeleeAnimationsTest`.

### 3.23 The Impact System (package `impact`)

A shared toolkit that makes hits feel heavy, like an anime fight: a hit lands with a short freeze, the camera shakes, a sharp flash
goes off where it met the body, and the biggest hits get a single black-and-white impact frame. Every hit goes through it: every
technique's damage, every melee hit, plain hits with no technique behind them (a sword, an arrow, a mob), and Swap's trades. It's
feel only: nothing in it changes what a hit does.

**Strength comes from what the hit did** (`ImpactStrength`, numbers in `[impact]` of the server toml), never a fixed number per
move. Everything that landed on one victim in one server tick is added up (`Impacts`), then:

  strength = damageWeight (1.2) × (damage dealt ÷ the victim's max health)
           + knockbackWeight (1.2) × (knockback beyond baseKnockback, the 0.4 every hit gets)
           + launchWeight (1.0) × (upward launch speed, blocks/tick) + chargeWeight (1.2) × (the charge it was cast at, 0 to 1)
           + maliceWeight (0.75) × (the base Malice behind the hit, per 100)

- Damage is what actually came off their health (`LivingDamageEvent.Post`), so armour, a guard and Rime Shell soften a hit's feel too.
- Knockback is stacked the way vanilla stacks it (each push halves what was there and adds its own): a hit's own 0.4 and a sprint's
  0.5 make 0.7. A throw that sets speed instead of pushing reports it (`Impacts.launch`: Glacial Spire).
- Charge: a projectile or spike that carries it (`ChargedHit`: Glacial Lance, Glacial Spire); Curio Burst's puppet tier (Tap 0,
  Half 0.5, Full 1); a Reinforced Strike counts as fully charged, and so does an ultimate.
- **The Malice behind it** (`CastMalice`): the base cost of the cast the hit traces back to (`Landings.baseCost` of what was paid,
  recorded when it's paid, so the surroundings and any discount never make a hit feel lighter, and Shatter Shell counts the 32 it
  cost with the shell up even though the shell is gone by the time it lands), plus the Malice a puppet carries when it goes off in
  a Curio Burst or a Chain Burst (what its tier cost to make: 40, 100 or 180). A melee hit with no cast behind it (a Reinforced
  Strike too) adds nothing.
- Hits that deal no damage still land on a body (`Impacts.hit`): Swap's moves (a plain swap, Exchange or Send Off is light; Momentum
  Exchange counts the speed it handed over; Total Swap counts the shares of health it moved, both ways, as its damage, and is an
  ultimate), and Shatter Shell's push. Abilities that never touch a body (Directive, Focus, Possess, Understudy, Stand-In, Strings'
  pulls, Awareness, Mimic, Anchor) make none.
- A hit the guard took some of (`GUARD_HIT`) lands one tier softer.
- Severed players' hits go through the same rule. They have no Malice, so that input is always 0 for them (nothing stands in for it).
  Their hits still reach every tier through damage, knockback and a Strike's full charge, and their Strike always lands harder than
  the same standard one (their bigger bonus and knockback): a punch is Light, a sprinting netherite hit Medium, an iron-sword Strike
  Heavy (2.37 against a standard player's 2.10), and a critical netherite Strike (21 damage) reaches the impact frame (3.00). That
  last is their only way there: a Malice user also reaches it with a full Glacial Spire, a Full Curio Burst or any Total Swap.
- The animations mark no impact tick of their own: they're timed to the server's moment (a melee reaction's key pose is its first
  frame; a clap meets as the swap lands), so the Impact System fires on those server moments.

**Tiers** (where each starts, in strength; the server's `[impact.tiers]`):

  | Tier | From | What lands like it (on a 20-health player) |
  |---|---|---|
  | Light | below 0.51 | a punch (0.06), a sword's normal hit, a Frost Shard, a plain swap (Positions, Exchange): it barely registers |
  | Medium | 0.51 | a sprinting or critical sword hit, a fist's Reinforced Strike, Shatter Shell's push (1.44 with the shell up, 1.86 without), the least Glacial Spire, Send Off, Switchback |
  | Heavy | 1.98 | an iron-sword Reinforced Strike (2.10), a full Glacial Lance (2.67), a Half Curio Burst |
  | Impact frame | 2.84 | a full Glacial Spire (3.66), a Full Curio Burst (3.57 a block away), every Total Swap (3.00 at equal health, 4.32 between 9/20 and 20/20) |
  | Top | never reached | reserved for Black Spark (not built): only a hit that asks for it |

  The numbers in brackets come from `/kegare debug impact log`. The weights were chosen so the rule itself puts each
  of those where it is, with no per-move minimum. The closest calls, about 5% from the line: a full Glacial Lance (2.67) and a Total
  Swap at equal health (3.00) either side of 2.84, and Shatter Shell's push (1.86) and an iron-sword Strike (2.10) either side of
  1.98. Configs from before the Malice input are moved to these numbers once (`KegareConfigMigration` version 4), unless edited.

**What each part does** (clients, `impact/client`). The server sends one `ImpactPayload` to the attacker, the victim and everyone
within `witnessRange` (48) of the hit: tier, where it met the body, which way it went, its color, and who attacked and who was hit.
Each client plays its own part:
- **Hit-stop** (`ScreenFx`): the frame the hit lands on is kept and shown again for the freeze, for the attacker and the victim only.
  It's the picture only: the game ticks on, the server is never delayed, damage and knockback land as they always did, keys are read
  as normal and the HUD stays live; when it ends you see where everything really is. The freeze and the impact frame count their
  time from the first frame they're drawn on, so a slow frame never swallows them.
- **Screen shake** (`ScreenShake`): the victim's stronger, the attacker's lighter (`attackerShake`, 45%). It starts as the freeze
  ends: a jolt the way the hit went (a recoil for the attacker), then a fast tremble dying away. Camera angles only, never anyone's
  aim or position. Nearby players get none.
- **Impact flash** (`ImpactFlash`): sharp and brief where the hit met the body, for everyone near: a hard white glint and spikes
  that shoot out and break away, solid and full-bright, gone in 3 to 6 ticks. White for a body or a weapon, the attacker's Malice
  color for a technique (its core stays white): the attacker sees their own color, everyone else the color of the face they wear
  (§1, §3.19). Never on your own body in your own first person, and smaller the closer it is to your camera.
- **Impact frame**: on the impact-frame tier and above, the attacker and the victim see one black-and-white high-contrast frame
  (`shaders/post/impact_frame.json`, Minecraft's own post-processing): brightness cut hard into black and white, read through a
  slight blur so textures don't turn to grain, with the outlines of shapes inked black. It's the first frame of the freeze.
  Everyone else sees the flash.
- **The screen shader hook** (`ScreenEffects`, `ScreenFx`): any post chain over one player's whole screen for a set time, from the
  server, fading in and out by its `Amount` uniform. Time Manipulation's Standstill uses it for its gray (`kegare:grayscale`, §3.26). `/kegare debug screen <player> <effect> <seconds>` plays one.

**The melee layer's moments** (§3.22) play by themselves at the tier `[impact.moments]` gives them: `DASH_BURST` a light shake for
the one dashing; `CLEAN_DODGE` a short freeze for the one who dodged; `PARRY_PERFECT` freeze, shake and a white flash for both
fighters (the parried attacker gets the stronger shake); `STAGGER` a shake for the one staggered. `STRIKE_HIT` makes its hit a fully
charged one, and `GUARD_HIT` makes its hit a tier softer.

**Each player's own look** (client toml, `[impact]`; all of it read live, so it can be tuned while the game runs):
`shakeStrength` (0 to 2) and `impactFrames` (on/off) are also on the Sorcerer screen's Settings page (§3.12); `hitStopStrength`,
`attackerShake`, `impactFrameMillis` (90), and for each tier `hitStopMillis`, `shakeDegrees`, `shakeMillis` and `flashSize`:

  | Tier | Freeze (ms) | Shake (degrees, ms) | Flash (blocks) |
  |---|---|---|---|
  | Light | 0 | 0.35, 140 | 0.22 |
  | Medium | 45 | 0.9, 220 | 0.36 |
  | Heavy | 90 | 1.8, 320 | 0.55 |
  | Impact frame | 150 | 3.0, 450 | 0.8 |
  | Top | 220 | 4.5, 650 | 1.1 |

`/kegare debug impact <player> <tier> <attacker|victim|witness> <melee|technique>` plays a tier on that player's own screen and nowhere
else, with nothing landing, so a tier can be felt and tuned without a fight. `/kegare debug impact log <on>` shows every hit's tier
and the numbers behind it (strength, damage of max health, knockback, launch, charge) to its attacker and victim, for tuning the
server's thresholds against real hits.

**Hit sounds** (`ImpactSounds`, Kegare's own from `tools/sounds/impact.py`, §3.10), at the point of contact and always with
vanilla's own hurt sound, never instead of it. A melee hit sounds like what it was hit with: `impact.punch` (an empty hand, or
anything that isn't a weapon: a heavy thud with a crack on top), `impact.blade` (a sword: a sharp swish with a slice),
`impact.heavy` (an axe or a mace: a heavier thud with a crunch); louder the harder it lands. Big hits of any kind (Heavy and up)
get `impact.boom` under them (a deep boom: 0.6 at pitch 1.1 for Heavy, 1.0 at 0.9 for the impact frame, 1.4 at 0.75 for Top).
Curio Burst adds its own thump (§3.20). Each has three versions to pick from in `run/sounds_preview/impact/` (`--preview`); the
first of each ships.

**Full, Reduced and Vanilla:** Full draws everything. Reduced draws fewer spikes and no impact frame. Vanilla draws vanilla's crit
sparks for the flash (dust in the Malice color for a technique) and no impact frame. Hit-stop and shake follow their own settings at
every quality. The impact frame needs the setting on and Full.

**Tests:** `ImpactTest` (the rule and its tiers, real hits resolving).

### 3.24 Battle damage (package `battledamage`)

Big hits damage the world. This changes fights on purpose: cover breaks and the ground changes mid-fight.

**Modes** (`[battle_damage] mode`):
- `PERMANENT` (default): what breaks stays broken.
- `RESTORING`: blocks rebuild themselves piece by piece once the fight has moved on (`BattleScars`). Each hit's blocks wait until
  there's been no battle damage within `quietRadius` (32) of them for `delay` (60 s), then come back one every `interval` (3)
  ticks: solid blocks first, lowest first, so what hangs on them (a torch, the top of a door) has something to hang on. What came
  down with a broken block (a torch on it, a door's other half) comes back too. A container comes back with its contents and never
  spills. A block comes back only where its space is empty again: never over something a player has put there since (a container
  that can't come back drops what it held there, so nothing is lost). A block with someone standing in it or right beside it
  waits for them to move, and the rest comes back round them. Pending rebuilds are
  saved with the dimension (`data/kegare_battle_scars.dat`), so a restart loses none, and they finish even if the mode is changed.
  `/kegare debug battle restore` starts them all now.
- `COSMETIC`: cracks and debris only; nothing breaks.

**What breaks it.** Only hits strong enough, read from the Impact System's strength (§3.23): a hit at `minimumTier` (Medium) or
above breaks blocks round where it met the body. Light hits never break anything. Swap never does (a clean magic trick). A hit by a
player or their technique always may; a mob's only with the `mobGriefing` gamerule on (`mobsNeedGriefing`).
- **Wall slams** (`WallSlams`): for `windowSeconds` (2.5) after a breaking hit its victim is watched. Knocked into a wall, a floor or
  a ceiling at `minSpeed` (0.9 blocks/tick; a sprinting hit knocks someone about 0.7) or more, stopping dead against blocks that
  way, they leave a crater where they hit: a hit of strength `strengthPerSpeed` (1.45) × speed at their edge. Speed is read from
  where they are each tick, so players and mobs alike. Landing from a full Glacial Spire's launch is one. Craters only: a slam does
  no damage of its own.

**One rule for what breaks** (`BattleDamage.breaks`): a hit's power is `strengthScale` (3) × its strength at the point of contact
(the top tier, reserved for a hit that asks for it: `topPower`, 1500), falling off in a straight line to nothing at its radius,
`baseRadius` (0.5) + `radiusPerStrength` (0.8) × strength, at most `maxRadius` (4.5). A block breaks where the power reaching it is
more than its blast resistance: glass 0.3 and dirt 0.5 go to almost anything that breaks at all, wood (3) to a solid hit, stone (6)
to a Heavy one at close range (a full Glacial Spire takes stone out to about 1.6 blocks), and obsidian (1200) only to the top tier.
- Never: blocks vanilla makes unbreakable (negative hardness: bedrock, barriers, End portal frames, command blocks, structure and
  jigsaw blocks, light blocks), fluids, and anything on the `protected` list (block ids and `#tags`; empty by default).
- Each block fires NeoForge's `BlockEvent.BreakEvent` first (as the attacking player, or a fake player for a mob), so spawn
  protection and claim or protection mods can cancel it; spawn protection, the world border and adventure mode are checked too.
- Nothing drops itself: broken blocks shatter into rubble, so a technique can't mine. What would have been knocked off them (a torch,
  a door's other half) doesn't drop either.
- A container spills its contents on the ground like TNT's (`spillContents`, on), and so does a lectern its book; in RESTORING mode
  they come back with the block instead.
- Performance: at most `maxBlocksPerHit` (40, the nearest first) per hit and `maxBlocksPerSecond` (160) per dimension, so a long
  fight can't lag the server.

**How it looks** (`BattleDamageClient`; the server sends one `BattleDamagePayload` with the blocks and what each was to players
within 96 blocks; the blocks change through the game's own updates):
- **Debris**: small solid chunks cut from the broken block's own texture (2 to 4 texels of its particle face, tinted as vanilla
  tints it), flung out from where the hit landed, tumbling, bouncing once and gone in under a second. Never drawn right in front of
  your own first-person camera. In COSMETIC mode they fly from the blocks that would have broken.
- **Cracks** on what survived: the surfaces round the hit (straight down, up and out each way from it) and the rim of the hole,
  nearest first. Pixel art on the blocks' own grid, 16 texels a block (`textures/marks/battle_crack`, near-black cracks with a pale
  broken lip and grit where it struck, built by `tools/blockbench/build_block_marks.py`), drawn by the same `BlockMarks` as Rime's
  frost. They reach further the more power was left at that face against what the block can take, and fade after 30 s.
- **Full** draws 5 chunks a block and up to 6 cracks round the hit and 5 on the rim; **Reduced** 2 chunks, 3 and 2 cracks;
  **Vanilla** vanilla's own block particles and no cracks.

**Tests:** `BattleDamageTest` (the rule, what never breaks, the protected list, no drops, spilling, both caps, a cancelled break
event, COSMETIC, RESTORING with contents and a restart, never over a block placed since, Swap and light hits, where a slam meets
the wall).

## 4. Extension points (how later content plugs in)

**Rule (every innate technique): the MOB vs PLAYER boundary.**
- **Physical effects** (damage, movement, freeze, knockback, status effects) work on mobs too, so every technique is
  useful outside PvP.
- **Identity effects** (disguises, health % swaps, and any future effect that reads or copies a player) are players
  only.
- **Bosses** (`c:bosses`) can be damaged but are never moved, swapped or disabled.
- **Advancements:** "learning" ones (first use; task frame) may count mobs. "Mastery" ones (goal or challenge frame,
  proving PvP skill) count PLAYER targets only (and player attackers, where someone else's hit is the condition).
- Where things stand:
  - The melee layer follows it (§3.22): parries stagger and Strikes knock back mobs too; bosses are never staggered or moved, and their hits are only reduced.
  - Swap follows it (§3.19): Positions, Switchback, Send Off, Exchange and Momentum Exchange take mobs; Awareness,
    Mimic and Total Swap are players only; bosses are never targets; its advancements split as the rule says.
  - Rime follows it (§3.14): its abilities hit mobs; bosses take the damage but get no Freeze stacks, no launch and
    no knockback. Every goal and challenge that names a target counts players only, and Thin Ice (goal) counts only
    damage blocked from players. Its task ones (Cold Open, Full Charge, Splinter) count players too, which the rule
    allows.
  - Puppet Manipulation follows it (§3.20): puppets fight mobs; bosses take Curio Burst, puppet and Tie damage but are never
    pushed, pulled or disabled; Stand-In copies only its owner. Pulling Strings, Out of Body, Kuru Kuru and Get Over Here count
    anything (not your own puppet, for Get Over Here); Nobody Home, Decoy, Who's Real?, Curiosity Killed, Little Me, Tied Up, Walkies
    and Strings Attached need a player.
  - The boss check is shared: `CombatHelper.isBoss` (`c:bosses`), used by Rime, `SwapTargeting` and Curio Burst.

- **New innate technique:** create a `DeferredRegister<InnateTechnique>` on
  `KegareRegistries.INNATE_TECHNIQUE_KEY`, build abilities with `BaseAbility`, add the lang names and an **epithet**
  (datagen fails without one), set a signature animation, **set unlock levels for its abilities, specials and ultimate**
  (datagen fails without them too), and put the numbers in config. Nothing in the base changes.
- **Refinement and Assessment:** every technique gets them through the shared path (`CastScope`, `Landings`, §3.21). Add code only where
  an ability lands without hurting (`Landings.land`), hits later (`Landings.during`), attacks through something else
  (`Attribution.addAttributor`) or has no target (`hasNoTarget`). A cost discount must be divided out in `Landings.baseCost`.
- **Other unlocks:** later ones register through `Unlocks.register` (§3.21), and the first-time sources they
  bring call `InsightHooks`.
- **Reading progression:** `Progression.getGrade(player)` on the server. Never send one player's
  Grade or Assessment to another.
- **Shared abilities:** build the ability, `SharedAbilities.register` it at mod construction, unlock it with
  `SharedAbilityService.unlock` (§3.16).
- **Specials:** override `special()` on the base ability and build the special on `SpecialAbility` (§3.15).
- **Swap immunity:** listen for `SwapTargetEvent` and cancel it (§3.19). **Seeing through disguises:** ask
  `Disguises` (`isDisguised`, `getRealIdentity`, `getDisguisedAs`), never what is drawn.
- **New trait:** register a `Trait` subclass (unique or not) and override its hooks.
- **Dominions:** an innate technique's `ultimate` ability. It uses `CombatHelper` (stun, combat) and the shared
  `CastManager.validate` checks. Dominion-specific state gets its own attachment.
- **Cost or cooldown modifiers** (e.g. from traits): `Ability.cost(player)` and `cooldownTicks(player)` already
  receive the caster. A CHARGED ability whose cost grows with the charge overrides `releaseCost(player, charge)`.
- **Taking over the keys** (a possession, a channelled state): `CastManager.addInterceptor` gets first say over every
  key intent and can swallow it (§3.20).
- **HUD from an innate technique:** `StatusLayer.addExtra` (a line under the crosshair, shown in and out of Technique
  Mode) and `CombatPanelLayer.addSlotDecorator` (marks on its own slots of the combat panel).
- **Soulless things:** anything that only works on living souls asks `Puppet#hasSoul()`.
